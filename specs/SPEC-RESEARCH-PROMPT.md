# 规格说明书（Spec）分层与生命周期研究 — 提示词

> 将此提示词发给其他大模型，分析规格说明书的类型体系、生成时机、以及最佳实践。

---

## 背景

我在做一个 SaaS 点餐小程序项目（NestJS + uni-app + Vue3 + MySQL + Redis）。项目采用多租户架构，涉及 3 个端（平台管理后台/商家管理后台/微信小程序）、26 个后端模块、122 个 API 端点。

项目已经产出了以下规格文档：

| 文档 | 行数 | 阶段 | 内容 |
|------|------|------|------|
| `docs/PRD.md` | 1758 | 需求阶段 | 产品需求规格说明书，18 轮审查封板 |
| `specs/SPEC.md` | 40 | 设计阶段 | 规格文档导航索引 + 技术栈速查 |
| `specs/ARCHITECTURE.md` | — | 架构设计 | 系统架构决策、多租户设计、部署拓扑 |
| `specs/DATA-MODEL.md` | 127 | 数据设计 | 全部数据库表、字段、关系、索引策略 |
| `specs/API-SPEC.md` | 172 | 接口设计 | 全部 REST API 端点、请求/响应格式、错误码 |
| `specs/STATE-MACHINES.md` | 97 | 逻辑设计 | 订单/团单/桌号/支付/商家状态机 |
| `specs/BUSINESS-RULES.md` | 114 | 逻辑设计 | 库存扣减、优惠计算引擎、退款规则、并发控制、编号规则 |
| `specs/MODULES.md` | 55 | 架构设计 | 模块清单、软硬依赖、权限矩阵、动态加载机制 |
| `specs/V1-SCOPE.md` | — | 规划阶段 | V1.0 范围清单、In/Out 明细 |
| `specs/QA-TEST-SPEC.md` | 1817 | 测试阶段 | 人工 QA 测试说明书，~198 条测试用例 |

目前正在设计**第 11 份文档**：`specs/AGENTIC-TEST-SPEC.md` — 面向 AI Agent 的可执行测试规格书。

## 研究任务

请你以**规格工程（Spec Engineering）**的视角，系统性地分析以下问题：

### 1. Spec 的分类体系

基于这个项目的 10+ 份规格文档，提炼一个**通用的 Spec 分类框架**。

需要考虑的维度：
- 按**生命周期阶段**分类（需求→设计→实现→测试→运维）
- 按**读者对象**分类（人类 vs 机器/Agent）
- 按**抽象层级**分类（业务层→逻辑层→物理层）
- 按**变更频率**分类（稳定 vs 随迭代演进）

请给出一个分类矩阵，将本项目的 10 份文档映射进去，标注哪些是"必须有的"、哪些是"锦上添花的"。

### 2. Spec 的生命周期 — 生成时机

每一类 Spec 应该在什么时间点生成？谁负责生成？谁负责维护？

请按以下时间轴分析：

```
签约 ──→ 需求评审 ──→ 架构设计 ──→ 数据库设计 ──→ 接口设计
  │         │           │            │              │
  │         │           │            │              ├─ 编码
  │         │           │            │              ├─ 单元测试
  │         │           │            │              ├─ 联调
  │         │           │            │              ├─ E2E 测试
  │         │           │            │              └─ 发版
```

针对每个时间点，标注：
- 应该产出什么 Spec
- Spec 的完成度要求（草稿 / 评审通过 / 封板）
- 如果缺失该 Spec，会在后续阶段造成什么后果

### 3. Spec 之间的依赖关系

本项目中，哪些 Spec 是单向依赖的（A 必须先于 B 完成）？哪些是双向交叉引用的？

例如：
- `PRD.md` → `API-SPEC.md`：API 端点从 PRD 功能需求推导
- `PRD.md` → `STATE-MACHINES.md`：状态机从 PRD 订单/团单流程提取
- `DATA-MODEL.md` ↔ `API-SPEC.md`：数据库字段和 API 响应字段互相约束
- `BUSINESS-RULES.md` → `QA-TEST-SPEC.md`：测试用例覆盖所有业务规则

请画出一个**依赖有向图（DAG）**。

### 4. Agentic Test Spec 的定位

我在本项目中新增了 `AGENTIC-TEST-SPEC.md`，它与传统 QA 测试说明书的区别是：

| 维度 | QA-TEST-SPEC（人读） | AGENTIC-TEST-SPEC（Agent 执行） |
|------|---------------------|-------------------------------|
| 格式 | Markdown 表格 + 自然语言 | 结构化 YAML + curl 指令 + JSONPath 断言 |
| 变量 | 无 | `{{token}}` `{{orderId}}` 跨步骤传递 |
| 断言 | "[ ] 库存不足返回 STOCK_INSUFFICIENT" | `HTTP 409` + `.code = "STOCK_INSUFFICIENT"` |
| 依赖管理 | 隐含在时序段落中 | `depends_on` 显式声明，形成 DAG |
| 执行者 | 人类 QA 工程师 | Claude Code Agent |

请分析：
- Agentic Test Spec 在整个 Spec 体系中应该放在什么位置？
- 它应该被视为 QA-TEST-SPEC 的"子集"还是"镜像"？还是独立的新品类？
- 在 AI 驱动的开发流程中，这种 Spec 是否会成为新的标准层？

### 5. 行业对标

请调研以下领域是否有类似的 Spec 分层实践：

- **NASA / 航空软件**：DO-178C 标准中软件生命周期数据（Life Cycle Data）的分类
- **汽车行业**：ISO 26262 功能安全中的软件规格分层
- **医疗设备**：IEC 62304 的软件文档要求
- **互联网企业**：Google / Amazon / Stripe 内部的 Design Doc / API Spec / Test Plan 体系
- **开源社区**：RFC 流程中的规范文档分类

对比本项目当前实践与行业标准之间的差距，给出改进建议。

### 6. 给我们的具体建议

基于以上分析，请针对本项目的规模（3 端、26 模块、122 API、~10 万行代码）给出：

1. **哪些 Spec 是当前缺失但应该补充的**？
2. **现有的 10 份 Spec 中哪些存在信息冗余**？（例如 STATE-MACHINES 的很多内容在 BUSINESS-RULES 中也有）
3. **Spec 的维护策略**：代码变更时，Spec 应该如何同步更新？是否应该引入 `spec-driven-development` 流程？
4. **Spec 的自动化**：哪些 Spec 可以从代码中自动生成（如 Swagger → API-SPEC），哪些必须手工维护？
