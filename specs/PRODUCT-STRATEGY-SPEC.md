# PRODUCT-STRATEGY-SPEC — 产品成功定义与需求拆解

> 本文用于补齐 PRD 中容易被功能清单掩盖的产品意图、首批客户画像、版本拆分、商业套餐、上线流程和验收指标。  
> PRD 定义“系统最终要有什么能力”；本文定义“第一阶段为什么做、先打穿什么、如何判断可卖可交付”。

---

## 1. 产品真实意图

本项目不是单客户定制点餐系统，也不是普通扫码点餐模板。真实目标是沉淀一个可复制销售、可 SaaS 租用、可源码买断、可模块化加价的微信点餐小程序模板产品。

一句话定位：

> 专为写字楼午高峰团餐设计的小程序点餐系统，帮助餐饮商家减少微信群接龙、人工统计、漏单错单和出餐混乱，同时支持独立品牌小程序、SaaS 托管和源码买断交付。

因此，产品优先级必须围绕三条主线排序：

1. **团餐效率**：让办公室团队点餐、截单、备餐、取餐更稳定。
2. **商家高峰处理**：让商家在午高峰少漏单、少错单、快确认、快出餐。
3. **可商品化交付**：让平台能按套餐开通、按模块裁剪、按流程交付。

积分、复杂优惠、预充值、平台精细运营是增强商业价值的模块，但不能压过上述三条主线。

## 2. 首批目标客户画像

### 2.1 ICP 定义

| 维度 | 首批优先客户 | 暂缓客户 |
|---|---|---|
| 店型 | 写字楼周边快餐、简餐、轻食、食堂档口 | 重堂食餐厅、纯外卖店、高端正餐 |
| 订单特点 | 午高峰集中、团体订单多、取餐节奏强 | 分散低频、客单高度定制化 |
| 规模 | 单店或 2-5 家小连锁 | 大型连锁总部复杂系统 |
| 现状 | 用微信群/电话/表格接团餐，人工统计痛点明显 | 已有成熟 POS/ERP 且强绑定 |
| 决策人 | 老板、店长、小连锁负责人 | 大型公司采购委员会 |
| 购买动机 | 少漏单、提高午高峰吞吐、沉淀私域、独立品牌 | 全渠道会员中台、复杂报表 |

### 2.2 真实痛点排序

| 优先级 | 痛点 | 对应产品能力 |
|---|---|---|
| P0 | 微信群接龙难统计、容易漏单错单 | 拼单、代表下单、团单明细、订单汇总 |
| P0 | 午高峰订单集中，后厨不知道先做什么 | 厨房模式、自动刷新、团单分组、一键出餐 |
| P0 | 支付和退款不清楚，人工对账麻烦 | 微信支付、订单状态机、退款审批、日对账 |
| P1 | 菜品上下架、售罄、规格价格维护麻烦 | 菜品/SKU/估清/定时上下架 |
| P1 | 老客户复购和活动运营弱 | 优惠券、积分、储值、折扣 |
| P1 | 想要自己的品牌小程序而不是平台店铺 | 品牌配置、独立 AppID、门店码 |
| P2 | 想买源码二开或部署到自己服务器 | 源码交付、模块裁剪、交付文档 |

## 3. 核心购买理由

销售和产品演示必须围绕以下 5 个理由展开：

| 购买理由 | 销售表达 | 必须演示的功能 |
|---|---|---|
| 减少群接龙和人工统计 | 团队员工自己选，系统自动汇总 | 创建团单、分享、加入、截单、团单明细 |
| 午高峰不乱 | 后厨大屏按订单和团单处理 | 厨房模式、待制作列表、批量出餐、打印 |
| 有自己的小程序 | 用户看到的是商家品牌，不是第三方平台 | 品牌配置、主题色、Banner、门店码 |
| 能做复购运营 | 后续可加券、积分、储值 | 优惠券、积分、预充值入口 |
| 可托管也可买源码 | 预算低用 SaaS，想二开买源码 | 模块套餐、源码交付包、License |

如果一个功能不能支撑这些购买理由，应降低 V1 优先级。

## 4. 版本拆解

现有 PRD 的 V1.0 是完整商用目标。实际交付应拆成四个递进版本，避免把全部闭环压进同一个验收口径。

### 4.1 Demo 可演示版

目的：支持销售演示和内部评审。

必须做到：

- C 端可浏览菜单、加购、提交订单。
- B 端可管理菜品、查看订单、切换订单状态。
- 团单可创建、加入、截单、查看明细。
- 厨房模式可展示待制作订单。
- 品牌配置可影响小程序基础展示。

允许限制：

- 支付可用 mock，但必须在界面和文档中标注演示模式。
- 打印可模拟。
- 退款、对账、订阅消息可以只展示入口。

### 4.2 试点可上线版

目的：支持 1-3 家真实商家试营业。

必须做到：

- 微信支付真实闭环：预支付、回调验签、幂等、主动查询。
- 订单状态闭环：待支付、已支付、已接单、制作中、待取餐、已完成、取消、退款中、已退款。
- SKU 库存乐观锁，支付超时释放或补偿机制。
- 团单至少支持 A 条件成团，截单后形成可备餐的订单/团单汇总。
- 厨房模式 5 秒内刷新新单，支持团单分组。
- 打印机至少真实接入 1 个品牌，并支持手动补打。
- 商家后台可完成菜品维护、订单处理、退款审批、营业设置。
- 数据看板至少包含今日营收、订单数、退款金额、Top 菜品。

不建议放入试点门槛：

- 积分商城。
- 商品券。
- 公司储值卡。
- 高级平台数据修正。
- 自动源码交付队列。

### 4.3 正式可销售版

目的：支持标准 SaaS 售卖和多商家运营。

必须做到：

- 平台后台可完成商家审核、模块开通、License、到期管理、版本记录。
- 商家上线流程标准化：资料收集、品牌初始化、菜单导入、支付配置、打印配置、小程序审核。
- 优惠券至少满减券闭环，接入结算和退款。
- 积分至少支持签到、消费入账、抵现，接入结算和退款。
- 订阅消息覆盖订单支付、接单、取餐、取消、退款等关键场景。
- 审计日志覆盖登录、订单、退款、菜品、配置、平台数据修正。
- QA/E2E/Agentic 测试覆盖 P0 流程。

### 4.4 源码交付版

目的：支持高客单价源码买断。

必须做到：

- 可按模块白名单裁剪源码，未购模块物理删除且编译通过。
- 交付包包含前端、后端、数据库迁移、部署文档、二开说明、License 信息。
- 打包过程生成 manifest，记录客户、模块、版本、时间、水印。
- 源码交付后支持本地文件存储或可配置 OSS。
- 明确售后边界：部署协助、Bug 修复期、二开支持范围、升级补丁策略。

## 5. 最小可卖版本

最小可卖版本不是最小代码量，而是能让首批客户愿意试用和付费的最小闭环。

### 5.1 必须打穿的三条闭环

#### 闭环 A：个人点餐

菜单浏览 → SKU 选择 → 购物车 → 提交订单 → 微信支付 → 商家接单 → 厨房制作 → 用户取餐 → 完成。

验收口径：

- 用户能在 2 分钟内完成一次下单支付。
- 支付成功后订单状态自动变为已支付。
- 商家能在后台确认接单并推进到待取餐。
- 库存不会因并发下单变成负数。

#### 闭环 B：团餐拼单

发起团单 → 分享 → 多人加入 → 截单 → 商家看到团单汇总 → 厨房按团单备餐 → 完成。

验收口径：

- 团单发起到分享不超过 30 秒。
- 参与者列表、菜品汇总、个人明细同时可见。
- 截单临界窗口不能继续加入。
- 商家端能按团单聚合查看和出餐。

#### 闭环 C：商家高峰处理

新订单提醒 → 订单列表 → 厨房大屏 → 打印/补打 → 批量出餐 → 今日对账。

验收口径：

- 午高峰 100 单模拟数据下列表不卡顿。
- 新单在厨房模式 5 秒内可见。
- 打印失败有明确补救动作。
- 老板能在 1 分钟内看懂今日营收、订单数、退款金额。

### 5.2 可延后但保留入口的能力

| 功能 | V1 处理方式 |
|---|---|
| 预充值 | 正式销售版或增值模块，试点期默认关闭 |
| 积分兑换商品 | V1.1，先做签到/消费/抵现 |
| 商品券 | V1.1，先做满减券 |
| 公司储值卡 | V1.5，需合规和财务规则明确 |
| 高级数据修正 | 平台内部工具即可，不进入商家端 |
| 自动源码交付队列 | 可先人工触发 packager |

## 6. 套餐与模块映射

### 6.1 SaaS 套餐

| 套餐 | 目标客户 | 包含模块 | 不包含 |
|---|---|---|---|
| 基础版 | 普通单店 | base、brand、order、dish、cart、payment、kitchen | group-meal、prepaid、points、coupon |
| 团餐版 | 写字楼高峰商家 | 基础版 + group-meal + printer + push-notify | prepaid、复杂营销 |
| 营销版 | 有复购运营诉求商家 | 团餐版 + coupon + points + discount | company prepaid |
| 旗舰版 | 小连锁/强运营商家 | 营销版 + prepaid + advanced platform support | V2 堂食/外卖 |

### 6.2 源码交付套餐

| 套餐 | 交付内容 | 模块策略 |
|---|---|---|
| 源码基础版 | 小程序、后端、商家后台、基础部署文档 | 删除团单、营销、储值、打印等未购模块 |
| 源码团餐版 | 基础版 + 团单 + 厨房 + 打印 | 保留 group-meal、printer、push-notify |
| 源码全模块版 | V1 全部 IN 模块 | 保留所有 V1 模块，附二开说明 |

### 6.3 模块降级要求

| 模块关闭 | C 端表现 | B 端表现 | 后端表现 |
|---|---|---|---|
| group-meal | 不显示拼单入口和团单分享 | 不显示团单菜单 | 拒绝团单 API 或返回模块未开通 |
| prepaid | 不显示余额/储值支付 | 不显示储值配置 | 禁止余额支付和充值 |
| coupon | 不显示券入口和结算券区域 | 不显示券模板管理 | 不参与结算 |
| points | 不显示积分入口 | 不显示积分规则 | 不产生积分和抵扣 |
| printer | 不显示补打/打印设置 | 不显示打印机菜单 | 不自动打印 |
| push-notify | 不请求订阅消息授权 | 不显示语音播报配置 | 不发送订阅消息 |

## 7. 商家上线交付流程

### 7.1 SaaS 上线流程

| 阶段 | 输入 | 平台动作 | 验收 |
|---|---|---|---|
| 签约 | 套餐、门店信息、联系人 | 创建客户档案 | 套餐和价格确认 |
| 资质收集 | 营业执照、食品经营许可证、身份证、门店照 | 平台后台审核材料 | 审核通过或退回原因明确 |
| 小程序准备 | AppID、主体信息、类目 | 绑定租户，配置 AppID | `/api/brand/config` 可返回租户配置 |
| 品牌初始化 | 店名、Logo、电话、主题色、Banner | 配置 BrandConfig | 小程序展示正确 |
| 菜单导入 | 菜品、分类、价格、库存、图片 | CSV 导入或后台录入 | 商家确认菜单正确 |
| 支付配置 | mchId、证书/APIv3 Key | 配置支付参数并做 1 分钱测试 | 支付回调成功 |
| 打印配置 | 设备品牌、编号、密钥 | 绑定打印机并测试小票 | 自动打印和补打成功 |
| 员工培训 | 老板/店长/收银/厨师账号 | 建账号、讲解流程 | 员工可完成本岗位动作 |
| 试营业 | 真实订单 | 平台陪跑 | 首日无 P0 阻断 |
| 正式上线 | 运营确认 | 归档上线资料 | 进入售后维护 |

### 7.2 源码交付流程

| 阶段 | 平台动作 | 交付物 |
|---|---|---|
| 确认购买模块 | 根据合同生成模块白名单 | 模块清单 |
| 生成交付包 | 执行 packager，裁剪未购模块 | 源码包、manifest |
| 编译验收 | 后端测试、后台 build、小程序 build | 验收截图/日志 |
| 部署指导 | 提供 Docker/MySQL/Redis/环境变量说明 | 部署文档 |
| 移交说明 | 说明二开边界、升级策略、售后期 | 交付确认单 |

## 8. 成功指标

### 8.1 产品可用指标

| 指标 | 目标 |
|---|---|
| 商家菜单初始化 | 1 天内完成首版菜单录入或导入 |
| 小程序配置 | 3 天内完成品牌、支付、打印配置 |
| 个人下单 | 用户 2 分钟内完成选餐支付 |
| 团单发起 | 发起人 30 秒内创建并分享团单 |
| 午高峰承载 | 100 单模拟数据下后台和厨房模式可正常操作 |
| 新单可见性 | 厨房模式 5 秒内看到新订单 |
| 打印失败恢复 | 商家能手动补打并看到失败原因 |
| 对账理解 | 老板 1 分钟内看懂今日收入、订单数、退款金额 |

### 8.2 商业验证指标

| 指标 | 目标 |
|---|---|
| 销售演示转化 | 演示后客户能明确选择套餐或提出采购问题 |
| 试点商家留存 | 试营业 7 天后仍继续使用 |
| 团单使用率 | 试点期团单订单占比达到 20% 以上 |
| 高峰人工减少 | 商家反馈人工统计时间明显减少 |
| 客诉阻断 | 无支付丢单、库存负数、退款错账等 P0 问题 |

## 9. 功能优先级重排

### 9.1 P0：不完成不能试点

- 微信登录和 JWT 刷新。
- 品牌配置和独立 AppID 租户识别。
- 菜品、分类、SKU、库存、估清。
- 购物车和下单。
- 微信支付真实闭环。
- 订单状态机、库存扣减、支付超时补偿。
- 商家订单处理和厨房模式。
- 团单基础闭环：创建、加入、截单、汇总、商家处理。
- 至少一个打印机品牌真实接入或稳定本地打印替代方案。
- 基础数据看板和日对账。

### 9.2 P1：正式销售增强

- 优惠券满减券闭环。
- 积分签到、消费入账、抵现。
- 订阅消息 5 个关键场景。

- CSV 导入导出。
- 源码交付 packager 可验收。

### 9.3 P2：增值或 V1.1+

- 预充值和公司储值卡。
- 商品券。

- 复杂折扣叠加。
- 高级报表。

- 企业认证和仅本公司可见团单。
- 堂食和外卖。

## 10. 高风险功能说明

### 10.1 预充值

预充值涉及资金账本、退款、用户注销、商家退出、微信审核和合规风险。不得作为普通营销功能处理。

上线前必须明确：

- 充值成功必须以支付回调为准，不得下单时直接入账。
- 余额消费、退款、冻结、解冻必须有流水。
- 商家到期、退出、注销时余额处理规则必须清晰。
- 用户注销时余额和券/积分资产处理规则必须清晰。
- 后台必须能对账：充值、消费、退款、余额。

### 10.2 团单

团单是核心卖点，必须做深。优先级高于积分商城和复杂营销。

上线前必须明确：

- 参与者支付模式：各自支付还是团长统一支付。
- 截单后的库存二次校验。
- 成团失败后的退款或释放规则。
- 厨房端团单聚合打印和出餐。
- 团单分享链接在未登录、已截单、已取消、已完成时的跳转行为。

### 10.3 源码交付

源码交付是高客单价能力，不等于压缩包。

上线前必须明确：

- 未购模块删除后必须编译通过。
- 交付包不得包含平台内部密钥、测试 token、生成产物。
- 保留水印或 manifest 追踪客户和版本。
- 明确二开支持和升级补丁边界。

## 11. PRD 补充结论

当前 PRD 的主要遗漏不是功能不够，而是缺少“产品成功定义”。后续所有需求评审应先回答：

1. 这个需求是否支撑团餐效率、商家高峰处理、可商品化交付三条主线？
2. 它属于 Demo、试点、正式销售还是源码交付版？
3. 它是否阻塞首批商家上线？
4. 它是否会引入支付、账本、退款、合规等高风险闭环？
5. 它是否能映射到具体套餐和销售话术？

若答案不清晰，应先补充本文，再进入 API、数据模型或页面开发。
