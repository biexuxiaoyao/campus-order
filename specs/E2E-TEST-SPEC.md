## 1. 测试策略

### 1.1 为什么按时序分层

系统存在严格的数据创建依赖链：

```
P端 创建 Tenant  ──→ B端 才能登录
B端 上架菜品    ──→ C端 才能看到正常菜单
B端 配置支付    ──→ C端 才能下单
```

跳过前面阶段直接测后面必然失败——不是代码 bug，是**前置数据不存在**。

### 1.2 测试角色

| 角色 | 账号 | 测试端 | 使用阶段 |
|------|------|--------|---------|
| 平台管理员 | `platform_admin` | P 端 API | 阶段 1-2 |
| 商家老板 | `admin` (自动创建) | B 端管理后台 | 阶段 3-5 |
| 商家店长 | `manager1` | B 端管理后台 | 阶段 5 |
| 收银员 | `cashier1` | B 端管理后台 | 阶段 5 |
| 厨师 | `chef1` | B 端管理后台 | 阶段 5 |
| C 端用户 A | `user_a` (微信登录) | 小程序 | 阶段 6-8 |
| C 端用户 B | `user_b` (微信登录) | 小程序 | 阶段 8 |

### 1.3 测试环境前置条件

```bash

docker start mysql-dev redis-dev
cd server && npx prisma migrate reset --force && npx ts-node prisma/seed.ts
```

### 2.1 为什么这个顺序不可更改

```
数据创建依赖链是单向的：

  没有 Tenant → B端无账号可登录 → 所有B端测试无法进行
  没有分类   → 无法创建菜品   → 所有C端测试看到"筹备中"
  没有上架菜品 → C端菜单为空  → 无法加购、无法下单
  没有支付配置 → C端下单被拒绝 → 订单链路中断
```

**违反时序的后果**：

| 如果先测 | 会发生什么 | 是 Bug 吗 |
|---------|-----------|----------|
| C端点餐（阶段7） | 菜单为空，无法下单 | ❌ 不是 Bug，前置数据缺失 |
| B端创建菜品（阶段4） | 无分类可选 | ❌ 不是 Bug，分类未创建 |
| B端登录（阶段3） | 403 TENANT_EXPIRED | ❌ 不是 Bug，License 未签发 |
| 拼单（阶段8） | 无菜品可选 | ❌ 不是 Bug，菜品未上架 |

### 2.2 阶段之间的数据传递

```
阶段 1 → 产出 {{tenant_id}} → 阶段 2/3/4/5 使用
阶段 3 → 产出 {{b_admin_token}} → 阶段 4/5/7 使用
阶段 3 → 产出 {{category_id}} → 阶段 4 使用
阶段 4 → 产出 {{dish_id_1/2/3}} → 阶段 7/8 使用
阶段 5 → 产出 {{b_manager_token}}, {{b_chef_token}} → 权限矩阵验证
阶段 6 → 产出 {{c_token_a}}, {{c_token_b}} → 阶段 7/8 使用
阶段 7 → 产出 {{order_id}}, {{pickup_no}} → 阶段 8 使用
```

### 2.3 阶段入口守卫

| 进入阶段 | 前置检查 | 不满足则 |
|---------|---------|---------|
| 阶段 2 | GET /api/admin/tenants/{{tenant_id}} → status=active | 阶段 1 未完成 |

## 3. 阶段 1 — P 端：商家入驻与审核

### 前置条件

- MySQL + Redis 已启动
- NestJS 服务运行中（http://localhost:3000）
- 平台管理员 JWT token 已获取

### E2E-1.1 创建 Tenant（正常流程）

**目标**：平台管理员创建一个新商家，系统自动生成 admin 账号和默认配置。

**角色**：平台管理员

| 步骤 | 操作 | API / 界面 | 预期结果 |
|------|------|-----------|---------|
| 1 | P端登录 | `POST /api/auth/admin-login` `{ username: "platform_admin", password: "..." }` | 返回 JWT token，role = "platform_admin" |
| 2 | 打开商家管理 | `GET /api/admin/tenants?page=1&pageSize=20` | 返回现有商家列表（至少含 seed 的 demo tenant） |
| 3 | 创建新商家 | `POST /api/admin/tenants` `{ appId: "wx_test_001", name: "老张私房菜" }` | 201，返回 Tenant 对象 |
| 4 | 验证自动创建 | 检查返回数据 | `licenseKey` 不为空（UUID），`status = "active"` |
| 5 | 验证 admin 账号 | `GET /api/merchant/staff?tenantId=<newId>` | 存在 username="admin" 的老板账号 |
| 6 | 验证默认配置 | `GET /api/brand/config` (Header: `x-app-id: wx_test_001`) | name="老张私房菜"，themeColor="#1A6EFF"，hours="08:00-20:00" |
| 7 | 验证菜单为空 | `GET /api/dishes?storeId=<storeId>` | items 数组为空，total=0 |
| 8 | 验证小程序状态 | (小程序端打开) | 首页展示"商家筹备中，敬请期待" |

**状态转换**：`无 → active`

**关键验证点**：
- [ ] licenseKey 由 `crypto.randomUUID()` 生成，不为空
- [ ] 初始 admin 账号密码通过邮件/短信发送（测试环境可查数据库验证）
- [ ] 默认 BrandConfig 使用签约时填写的商家名
- [ ] 0 分类、0 菜品

**角色**：平台管理员

### E2E-1.3 入驻审核

**目标**：验证审核流程的两条分支（通过 / 驳回）。

**角色**：平台管理员

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 创建待审核商家 | `POST /api/admin/tenants` `{ appId: "wx_test_002", name: "待审餐厅" }` |
| 2a | **分支A：审核通过** | `POST /api/admin/tenants/<id>/review` `{ approved: true }` → status="active" |

| 3 | 验证审计日志 | `GET /api/merchant/audit-logs` | 包含审核操作的记录 |

**状态转换**：`审核中 → active（通过）| deleted（驳回）`

### E2E-2.2 License 签发与吊销

**目标**：验证 License 全生命周期。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 签发 License | `PUT /api/admin/tenants/<tenantId>/license` `{ action: "issue" }` | licenseKey 更新为新 UUID |
| 2 | 验证商家正常访问 | B 端 / C 端均可正常访问 | — |
| 3 | 吊销 License | `PUT /api/admin/tenants/<tenantId>/license` `{ action: "revoke" }` | licenseKey=null, status="expired" |
| 4 | 验证 B 端被拒绝 | 商家尝试登录管理后台 | 403 `TENANT_EXPIRED` |

| 6 | 重新签发恢复 | `PUT .../license` `{ action: "issue" }` | 商家恢复正常访问 |

**状态转换**：`active → expired（吊销）→ active（重新签发）`

## 5. 阶段 3 — B 端：首次登录与引导初始化

### E2E-3.1 首次登录 → 强制修改密码

**目标**：商家老板使用初始密码登录，系统强制修改密码。

**角色**：商家老板（admin）

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 打开管理后台 | 浏览器访问 http://localhost:5173 | 显示登录页 |
| 2 | 输入初始密码 | `username: "admin"`, `password: <初始密码>` | — |
| 3 | 验证强制跳转 | 点击登录 | 跳转到修改密码页面（非 dashboard） |
| 4 | 尝试绕过改密 | 手动访问 `/dashboard` | 重定向回修改密码页 |
| 5 | 输入新密码 | 新密码：`"NewP@ss123"` (8位+大小写+数字) | — |
| 6 | 提交 | 点击确认 | JWT 刷新，自动跳转 `/dashboard` |
| 7 | 再登录 | 退出后重新登录 | 用新密码 `"NewP@ss123"` 可成功登录 |

**关键验证点**：
- [ ] 首次登录（`passwordChanged=false`）强制跳转修改密码页
- [ ] 改密前无法访问其他任何页面
- [ ] 密码强度校验生效（8位+大小写+数字）
- [ ] 新密码用 bcrypt 存储，数据库中不可逆

### E2E-3.3 登录态与异常

| 用例 | 操作 | 预期结果 |
|------|------|---------|
| **JWT 过期** | 等待 12h 或使用过期 token | 401 `AUTH_EXPIRED`，前端自动跳转登录 |
| **暴力破解锁定** | 连续 5 次输入错误密码 | 第6次：`"账号已被锁定，请15分钟后再试"` |
| **锁定后解锁** | 锁定期间尝试正确密码 | 仍然拒绝 |
| **15分钟后** | 等待 15 分钟后正确登录 | 登录成功，`lockedUntil` 清除 |
| **忘记密码** | 点击忘记密码 → 手机验证 → 重置 | 重置成功后自动解锁 |
| **退出登录** | 点击退出 → 手动访问 `/dashboard` | 跳转登录页，localStorage token 已清除 |
| **多个错误后正确** | 3次错误 + 1次正确 | 成功登录，`loginAttempts` 重置为 0 |

### E2E-8.5 优惠叠加计算

**目标**：验证折扣→优惠券→积分的严格计算顺序。

**前置**：订单原价 ¥100（10000 分）

| 步骤 | 配置 | 计算过程 | 预期结果 |
|------|------|---------|---------|
| 1 | — | 订单原价 | 10000 分 |
| 2 | 满减规则：满 80 打 9 折 | 10000 × 0.9 | 9000 分 |
| 3 | 优惠券：满 50 减 10 | 9000 - 1000 | 8000 分 |
| 4 | 积分抵现：500 分 = ¥5 | 8000 - 500 | 7500 分 |
| 5 | 微信支付 | — | 实付 ¥75.00 |

**验证点**：
- [ ] 计算顺序不可更改（折扣→券→积分→支付）
- [ ] 不可叠加规则仅取最高优先级
- [ ] 可叠加规则按优先级依次计算
- [ ] 优惠券自动匹配最优
- [ ] 用户可手动切换优惠券
- [ ] 不可用券展示 + 不满足条件标注
- [ ] 凑单提示（差距 ≤ ¥5 时显示"再加 ¥X 可享 XX 优惠"）
