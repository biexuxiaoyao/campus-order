## 1. 产品概述

### 1.1 产品定位

本产品是一个**可售卖的微信点餐小程序 SaaS 模板**。目标客户是写字楼周边的餐饮商家。

**多租户架构**：每个商家拥有独立的微信小程序 AppID，后端共享一个服务实例，通过请求中的 AppID 识别租户并隔离数据（`tenant_id`）。C 端用户打开的是某个商家的小程序，只看到该商家的菜品和品牌，不存在"切换商家"的 C 端场景。

| 交付形态 | 说明 |
|---|---|
| **SaaS 租用** | 商家按年付费，我们托管服务器（共享后端），商家使用自己的小程序 AppID |
| **源码交付** | 商家买断源码，自行部署独立实例。源码经过处理——不暴露模板的配置系统和未购买模块。详见 3.13 源码交付 |

### 1.2 目标用户

- **B 端（商家）**: 写字楼周边的快餐店、简餐店、食堂档口，需要高效处理团体订餐
- **C 端（消费者）**: 写字楼内的上班族，以公司/团队为单位的团体订餐场景
- **P 端（平台运营方）**: 我们——管理商家入驻、版本升级、License

### 1.3 核心场景

| 场景 | 描述 |
|---|---|
| ① 个人点餐 | 用户在小程序选菜 → 支付 → 商家接单 → 备餐 → 用户取餐 |
| ② 拼单模式 | 发起人创建团单 → 分享到公司群 → 同事各自加入选餐支付 → 截单 → 商家统一备餐 |
| ③ 代表下单 | 行政/前台统一帮团队选餐 → 统一下单支付 → 商家接单备餐 |
| ④ 堂食点餐 | 用户扫码桌号 → 点餐 → 支付 → 厨房出餐 → 服务员送餐到桌 |

## 2. 用户角色

### 2.1 C 端角色（小程序用户端）

| 角色 | 说明 |
|---|---|
| **普通用户** | 微信登录后的消费者，可以点餐、参与拼单 |
| **团单发起人** | 创建团单的普通用户，可以手动截单 |
| **企业认证用户** | 完成企业认证的用户，可以创建"仅本公司可见"的团单 |
| **代表下单人** | 通常为行政/前台，有权限为团队统一下单 |

### 2.2 B 端角色（管理后台）

| 角色 | 权限范围 |
|---|---|
| **老板（超级管理员）** | 全部权限，包括退款审批、模块购买/续费、员工管理/角色分配、完整财务报表、营业设置修改。老板可兼任店长 |
| **店长（管理员）** | 菜品管理、订单处理（确认接单/取消订单/修改备注）、查看当日营业数据。**不可**：退款审批、员工管理、查看完整财务报表、修改营业设置 |
| **收银员** | 订单处理（确认接单/取消订单、发起退款申请）、查看当日订单。**不可**：退款审批 |
| **厨师/备餐员** | 查看待制作订单、更新订单状态（制作中→已完成） |

### 2.3 P 端角色（平台运营）

| 角色 | 权限范围 |
|---|---|
| **平台管理员** | 商家入驻审核、模块分配、License 签发、查看大盘数据 |
| **平台开发** | 模板版本发布、打包交付、升级补丁管理 |

## 3. 功能需求

### 3.1 品牌配置化（P0）

**需求**: 商家的品牌信息不在代码中写死，通过后台配置并实时生效。

| 配置项 | 说明 | 影响范围 |
|---|---|---|
| 小程序名称 | 展示在微信顶部导航栏 | 小程序全局 |
| 商家名称/Logo | 展示在首页、订单页 | 所有页面 |
| 联系电话 | 用户点击拨打 | 首页、订单详情 |
| 主题色 | 主色调、辅助色 | 导航栏、按钮、标签 |
| 顶部 Banner | 首页轮播图（最多 5 张，3 秒自动轮播，可按时段投放不同 Banner） | 首页 |
| TabBar 图标 | 底部导航图标 | 全局 |
| 营业时间 | 商家营业时段 | 下单时校验 |
| 微信支付商户号 | mchId、APIv3 密钥 | 支付流程 |
| 分享配置 | 分享标题、分享图片 | 微信分享卡片 |
| 门店小程序码 | 商家可在管理后台下载专属小程序码（带商家Logo），提供多种尺寸（适合打印的300dpi PNG），用于海报/桌贴/门口立牌。永久有效，除非手动重新生成 | 线下引流 |

**图片配置说明**：Logo 和 Banner 图片通过统一上传接口（见 3.17）上传，存储路径纳入租户隔离体系。

**验收标准**:
- [ ] 管理后台修改品牌配置后，小程序端在下次启动时生效（重新拉取配置）。小程序启动时若配置接口不可用，使用上次成功缓存的本地配置 + 顶部提示"网络异常，使用缓存数据"
- [ ] 不同商家的同一套小程序代码（不同 appId），拉取到不同的品牌配置
- [ ] 品牌配置支持 JSON 扩展字段，商家二开可自定义新增配置项

### 3.2 模块化业务架构（P0）

**需求**: 每个业务功能作为独立模块，商家按需购买和启用。管理后台和小程序端根据已购买模块动态展示功能入口。

#### 3.2.1 模块清单

| 模块 ID | 模块名称 | 功能概要 | 硬依赖 | 软依赖（可选联动） |
|---|---|---|---|---|---|
| `base` | 基础模块 | 商家信息、菜品管理、个人点餐、微信支付、订单管理 | 无（必选） | — |
| `group-meal` | 团体订餐 | 拼单模式 + 代表下单模式 | `base` | `prepaid`（公司储值卡支付）、`discount`（团单折扣）、`points`（团单积分） |
| `dine-in` | 堂食点餐 | 桌号管理、扫码点餐、服务员端 | `base` | `prepaid`（储值卡支付）、`printer`（后厨打印） |

| `points` | 积分系统 | 消费积分、积分兑换、积分抵现 | `base` | `coupon`（积分兑换优惠券） |
| `coupon` | 优惠券 | 满减券/折扣券/商品券、发放和核销 | `base` | `points`（积分兑换券）、`discount`（叠加计算） |
| `advanced-stats` | 高级报表 | 品类分析、时段分析、用户画像 | `base` | — |
| `printer` | 小票打印 | 对接云打印机，自动/手动打印小票 | `base` | — |
| `push-notify` | 消息推送 | 微信订阅消息、语音播报 | `base` | — |

> **软依赖说明**：软依赖模块未购买时，关联功能自动降级或隐藏（如未购买 `prepaid` 时，支付方式不展示"公司储值卡"选项）。硬依赖模块未购买时，该模块整体不可用。

#### 3.2.2 模块管理行为

**管理后台**:
- [ ] 左侧菜单根据已购模块动态生成
- [ ] 未购买模块左侧菜单不显示该入口

**验收标准**：

- [ ] 源码交付包中不存在未购买模块的任何代码或配置。

### 3.3 个人点餐（P0）

**需求**: 用户在商家小程序中自主选餐、下单、支付、取餐。

#### 3.3.1 菜品浏览
- [ ] 按分类展示菜品列表（分类 Tab 导航）
- [ ] 展示菜品图片、名称、价格、月销（近 30 天已支付且未退款的售出份数）
- [ ] 菜品详情页：大图、描述、规格选择（SKU 笛卡尔积模式，见 3.11.2.1）
- [ ] 支持"常点清单"：聚合用户历史高频订单
- [ ] 支持菜品售罄标记（实时库存，售罄规格置灰不可选）
- [ ] 支持多时段菜单（早餐/午餐/下午茶自动切换）。切换时间点按商家设置的营业时段整点触发。用户当前已在浏览菜单时不做强制刷新，下次进入菜单页时拉取最新时段数据。
- [ ] 支持过敏原/忌口标注（辣度、含猪肉、花生等）
- [ ] **菜品搜索**：菜单页顶部搜索框，支持菜品名称模糊搜索（中文分词）。V1.0 不支持拼音搜索和语音搜索。搜索结果按匹配度和月销排序
- [ ] **菜单缓存策略**：菜品列表接口响应缓存 60 秒（服务端），下单/购物车操作时不走缓存（实时查询库存）。商家修改菜品后主动清除该租户的菜单缓存
- [ ] **菜单联动交互**（对标行业最佳实践）：
  - 左侧分类栏点击 → 右侧商品列表自动滚动定位到对应分类，目标分类高亮
  - 右侧商品列表独立滚动 → 左侧分类栏自动跟随高亮当前可见分类
  - 当前高亮分类被遮挡时，自动调整滚动位置至可见
  - 分类栏支持横向滑动（分类数量多时）
- [ ] **价格呈现规范**（三段式设计）：
  - ¥ 符号小号、整数部分大号加粗、小数部分小号（如 <span style="font-size:12px">¥</span><span style="font-size:20px;font-weight:bold">9</span><span style="font-size:12px">.9</span>）
  - 原价使用灰色删除线展示
  - 优惠价使用品牌主色突出

#### 3.3.2 购物车
- [ ] 添加菜品到购物车（含规格选择，使用 Stepper 步进器组件）
- [ ] 修改数量、删除
- [ ] 购物车汇总金额
- [ ] 清空购物车
- [ ] **购物车数量上限**：单个用户购物车最多 20 件商品（不同 SKU 计为不同件），超出时提示"购物车已满，请先结算"
- [ ] **购物车存储**：购物车数据存储在服务端（按 userId + tenant_id 隔离），切换设备后购物车内容不丢失。用户退出小程序后购物车保留 24 小时自动清空。
- [ ] **购物车异常处理**：用户再次进入购物车或提交订单时，后端校验购物车中每个菜品——已下架/已删除的商品自动移除并提示"XXX 已下架，已从购物车移除"；库存变为 0 的提示"XXX 已售罄"并移除；价格变动的商品保留但提示价格变化（显示新旧价格对比）。
- [ ] **购物车吸底规范**：
  - 购物车组件固定在页面底部（吸底悬浮），不随页面滚动
  - 有商品时显示商品数量红色角标（带弹性动画）
  - 无商品时角标消失，购物车图标置灰
  - 点击购物车弹出抽屉面板，展示已选商品清单
- [ ] **Stepper 步进器交互**：
  - 数量 = 0 时仅显示蓝色圆形 [+] 按钮（最小化视觉干扰）
  - 数量 ≥ 1 时展开为 [-] [数量] [+] 三段式步进器
  - 点击 [+]/[-] 时带弹性缩放动画

#### 3.3.3 下单
- [ ] **取餐方式顶层切换**：菜单页顶部 Tab「堂食 / 自取 / 外卖」，先选场景再浏览菜单。V1.0 只做「自取」，堂食和外卖的 Tab 预留但置灰（标注"即将上线"）。
- [ ] 选择取餐时间（立即取餐 / 预约取餐时段）。预约以 15 分钟为粒度（如 11:00-11:15），商家可设置可预约的时间窗口（如仅接受 11:00-13:00 的预约）。预约取餐同样在下单时预占库存。取餐日当天凌晨转为确认扣减。
- [ ] 填写备注（快捷备注标签 + 自定义备注）。自定义备注 ≤ 100 字，前端实时显示剩余字数。快捷备注标签由商家在后台预设（如"少油""加辣""不要香菜"），最多 10 个标签
- [ ] 选择支付方式：微信支付 / 个人余额 / 公司储值卡（若开通预充值模块，见 3.5）
- [ ] 提交订单 → 支付 → 生成取餐号
- [ ] **价格锁定**：提交订单时以当前菜品价格生成订单快照（保存到 OrderItem 中）。商家后续改价不影响已提交但未支付的订单。支付超时取消后订单不保留，下次下单按新价格计算。

#### 3.3.4 订单管理（用户端）
- [ ] 订单列表（按状态 Tab：全部/待支付/进行中/已完成）
- [ ] 订单详情：菜品清单、金额、取餐号、状态

**订单编号规则**：
- [ ] **个人订单号**：`{YYYYMMDD}{HHmmss}{6位随机数}`，如 `2026061714320918A7F2`。全局唯一（跨租户不重复）。
- [ ] **取餐号**：每个订单生成简短的取餐号，格式 `A{3位自增数字}`，如 `A001`。每日从 001 开始，按当日订单顺序递增。取餐号用于顾客取餐时识别。
- [ ] **团单号**：`G{YYYYMMDD}{HHmmss}{4位随机}`，如 `G20260617143209A7F`。
- [ ] **团单子编号**：取餐号后加 `-N` 后缀，如团单取餐号 `A005`，3 个参与者各自的子编号为 `A005-1`、`A005-2`、`A005-3`。
- [ ] **订单时间轴可视化**：订单详情页使用时间轴展示每个状态节点及时间戳——
  ```
  ① 下单成功     14:32
  ② 已支付       14:32
  ③ 商家已确认    14:35
  ④ 制作中       14:38
  ⑤ 备餐完成，待取餐 14:50
  ⑥ 已取餐       15:02
  ```
  当前所在节点高亮，已完成节点打勾，未到达节点置灰。节点变动时实时更新。
- [ ] **再来一单**（多入口）：
  - 订单列表页：每个已完成订单旁「再来一单」按钮
  - 订单详情页：「再来一单」按钮
  - 首页常点清单：「再来一单」快捷入口
  - 防重：点击后按钮置灰 + loading，3 秒内不可重复点击。后端对相同用户+相同原订单的"再来一单"在 5 秒内去重
- [ ] 申请退款（商家审核）
- [ ] 订单状态流转：
  ```
  待支付 ──→ 已支付 ──→ 商家已确认 ──→ 制作中 ──→ 待取餐 ──→ 已完成
     │           │            │            │          │          │
     ├─ 超时自动取消        │            │          │          │
     └─ 用户手动取消        │            │          │          │
                 │           │            │          │          │
                 ├─ 用户取消 ─────────────┤          │          │
                 ├─ 商家取消 ─────────────┤          │          │
                 │                        │          │          │
                 └─ 退款中 ───────────────┤          │          │
                     │    （商家同意）     │          │          │
                     ├─ 已退款             │          │          │
                     └─ 商家拒绝 → 回到退款前状态          │
                                                         │
                  ←←←←← 所有非"已完成/已取消/已退款"状态均可发起退款申请 ←←←←←
  ```
  - "待支付"状态下：用户可手动取消；倒计时超时系统自动取消
  - 退款申请时效为支付成功后 24 小时内（商家可调），即"已完成"状态的订单在 24 小时内仍可申请退款
  - 商家拒绝退款后，订单回到发起退款前的状态（如原为"制作中"则回到"制作中"，原为"已完成"则回到"已完成"）
  - 营业结束时，所有"待取餐"订单由系统自动标记为"已完成"（商家也可手动提前标记）

#### 3.3.5 订单超时与库存释放规则

**需求**：自动处理订单支付超时、商家接单超时，并确保库存回滚。

| 触发事件 | 逻辑 | 配置项 |
|---|---|---|
| 用户提交订单后未支付 | 倒计时 N 分钟未支付 → 自动取消 → 恢复库存 | 支付超时时间（商家可配，默认 15 分钟） |
| 用户支付后，商家未确认 | 倒计时 M 分钟商家未操作 → 系统自动确认（或自动退款，按开关） | 自动接单开关 + 超时时间（默认 10 分钟） |
| 拼单截止时库存不足 | 部分子订单支付成功但库存不足 → 缺货的订单自动退款，其余正常提交 | 不可超卖，需实时扣库存 |

**验收标准**：
- [ ] 支付倒计时在订单提交后前端开始展示，超时后订单自动取消，库存原子性恢复。
- [ ] 商家可在管理后台设置"支付超时时间"和"自动接单"选项。
- [ ] 库存不足时子订单退款，且用户收到"部分菜品已售罄"的提醒。

#### 3.3.6 退款与结算规则

**需求**：定义退款全流程的时效、金额计算和争议处理。

**规则明细**：
- [ ] **退款申请时效**：订单支付成功后 24 小时内可申请（商家可调整），超时入口隐藏。
- [ ] **部分退款**：
  - 指定某一/几份菜品退款，按菜品原价退款，优惠按比例分摊（满减/折扣/优惠券优惠等比分摊到每个商品）。
  - 退款后若订单金额不满足原优惠门槛，优惠重新计算（已退部分补扣差额）。
- [ ] **全额退款**：订单金额全额退回用户支付账户。
- [ ] **资金到账时间**：微信支付/余额支付原路退回，微信侧到账时间由微信决定，系统仅调用退款接口。
  - **退款路径明细**：微信支付 → 退回微信；个人余额支付 → 退回个人余额；公司储值卡支付 → 退回公司储值卡。按各支付来源所占金额比例原路退回。
- [ ] **支付手续费**：微信支付费率 0.6% 由商家承担。订单金额=用户实付金额，商家净收=用户实付-手续费。管理后台展示手续费支出明细
- [ ] **优惠券处理**：已使用的优惠券退款后不退还。退款金额按优惠后实付金额及优惠分摊比例计算。
- [ ] **商家审核**：退款申请在管理后台弹出，商家可同意/拒绝；拒绝需填写原因，用户可看到。
- [ ] **争议升级**：若商家拒绝后用户再次发起，需填写额外说明。第二次拒绝后标记为"争议中"，并在平台管理后台展现（V1.0 暂不做平台介入，仅记录）。同一订单最多申请 2 次退款。

**验收标准**：
- [ ] 部分退款时优惠分摊计算准确，订单详情展示清晰退款明细。
- [ ] 退款金额按原支付方式返回，无二清问题。
- [ ] 退款完成后用户微信收到退款到账通知。

#### 3.3.7 催单（P1）

**需求**：用户等待超时后可主动催单，商家端收到提醒。

- [ ] **催单入口**：订单详情页「待取餐」状态下显示「催单」按钮。
- [ ] **催单规则**：
  - 订单支付成功后 N 分钟才显示催单按钮（商家可配，默认 10 分钟，避免刚下单就催）。
  - 同一订单最多催 M 次（默认 3 次），超过后提示"已催促，请耐心等待"。
  - 每次催单间隔 ≥ 5 分钟。
- [ ] **商家端响应**：
  - 管理后台该订单高亮闪烁 + 语音播报"订单 #XXX 被催单"。
  - 厨师端/服务员端该订单置顶显示。
  - 商家可回复"预计还需 X 分钟"，用户端同步展示。
- [ ] **V1.0 范围**：仅催商家备餐，不涉及催骑手（外卖配送模块为 P2）。

**验收标准**：
- [ ] 催单按钮在符合条件时正确显示/隐藏。
- [ ] 商家端收到催单后高亮 + 语音提醒生效。
- [ ] 超次数后催单按钮置灰并提示。

#### 3.3.8 并发安全与防超卖（P0）

**需求**：午餐高峰高并发场景下防止库存超卖和状态冲突。

**库存扣减机制**：
- [ ] **下单 → 预占库存**：用户提交订单时扣减"可用库存"（SKU.available_stock -= quantity），支付超时或用户取消时回滚。
- [ ] **支付成功 → 确认扣减**：已预占的库存正式扣减（无需再次操作库存）。
- [ ] **支付超时/取消 → 释放预占**：回滚预占库存（SKU.available_stock += quantity）。
- [ ] **并发保护**：库存扣减使用乐观锁（version 字段），更新失败时重试最多 3 次，仍失败返回"下单繁忙，请重试"。

**截单临界窗口处理**：
- [ ] 截单时间到达后，先禁止新参与者加入，等待 30 秒让进行中的支付完成，再执行合并。
- [ ] 30 秒缓冲期内支付成功的正常合并，支付失败的子订单取消并释放库存。
- [ ] 缓冲期内用户端展示"截单中，请稍候..."。

**代表下单支付前二次校验**：
- [ ] 代表提交订单时，后端重新校验每个菜品的当前库存。
- [ ] 库存不足的菜品自动从订单中移除，提示"以下菜品已售罄：XXX"。
- [ ] 所有菜品售罄时阻止下单。

**商家并发操作防护**：
- [ ] 所有订单状态变更操作（确认/取消/完成备餐等）使用乐观锁。
- [ ] 操作前校验当前状态是否允许该操作（如"已取消"的订单不可再点"完成备餐"）。
- [ ] 并发冲突时后操作者收到"订单状态已变更，请刷新后重试"。

**验收标准**：
- [ ] 并发压测：100 人同时抢最后 10 件库存，最终仅 10 单成功，无超卖。
- [ ] 截单缓冲期内支付成功正常合并，缓冲期后支付被拒绝。
- [ ] 并发操作同一订单时，仅一方成功，另一方收到冲突提示。

### 3.4 团体订餐（P0）

**需求**: 支持两种团餐模式。

#### 3.4.1 拼单模式

**流程**:
```
发起人创建团单
  → 选择商家、设置截止时间、设置团单可见范围（全楼/仅本公司）（V1.0 仅支持"全楼"，"仅本公司"依赖企业认证模块 P2）
  → 选择拼单成立条件（A: 达到最低金额即成立 / B: 全员支付成功才成立）
  → 生成团单分享卡片（卡片内容：商家名称、团单发起人头像昵称、截止时间倒计时、已参与人数、最低起订金额达成进度）→ 分享到微信群
  → 同事点击卡片加入团单，各自选餐
  → 各自支付（微信支付/余额）
  → 截止时间到，或发起人手动"截单"
  → 系统合并为一个团单，推送给商家
  → 商家统一备餐
  → 发起人或指定人到店统一取餐
```

**规则**:
- [ ] 团单截止时间默认发起后 30 分钟，可自定义
- [ ] 截止时间前，参与者可修改/取消自己的订单
- [ ] 截止时间后，所有参与者订单锁定
- [ ] 发起人可手动提前截单
- [ ] 若截止时间到无人参与，团单自动取消
- [ ] 发起人可指定取餐人（默认发起人）
- [ ] 团单合并后，商家看到的是"1 个团单，包含 N 份餐"
- [ ] 团单支持最低起订金额（商家设置）
- [ ] **拼单成立条件**：发起人创建时选择
  - A. 达到最低起订金额即成立（允许部分参与者支付失败，已支付的合并提交）
  - B. 所有参与者必须支付成功才成立（任一失败整单取消，已付者自动退款）
- [ ] **支付失败处理**：选择 A 模式时，截止时已支付的子订单合并提交，未支付的子订单自动取消并恢复库存；选择 B 模式时，任一失败，所有已支付订单自动退款，团单取消。

**团单状态机**：
```
拼单中 ──→ 已截单 ──→ 已合并提交 ──→ （跟随主订单状态）
   │           │
   └─ 已取消    │（发起人截单 / 截止时间到自动截单）
 （无人参与 /   │
  发起人取消）  │

代表下单模式：
  已创建 ──→ 已提交 ──→ （跟随主订单状态）
```
- [ ] 拼单截单后，团单下的所有已支付子订单合并生成一个主订单，推送给商家。主订单使用团单号作为取餐号，各子订单保留独立编号。
- [ ] 若团单仅发起人一人参与，仍按团单流程处理（不降级为个人订单）。
- [ ] 发起人取消自己的子订单时，团单仍有效；若发起人是唯一参与者且取消，团单自动取消。
- [ ] **团单分享链接处理**：用户点击团单分享卡片 → 小程序打开 → 判断团单状态：仍在"拼单中"→ 展示团单详情引导加入；已截单/取消 → 展示"该团单已结束" + 个人点餐入口。未登录用户先展示团单预览页（可浏览菜品但不可加入），点击"加入团单"时触发微信登录，登录后自动跳回团单详情页

#### 3.4.2 代表下单模式

**流程**:
```
代表打开小程序
  → 选择"代表下单"模式
  → 为团队选餐（可指定每份餐的归属人姓名）
  → 统一下单
  → 统一支付（微信支付/余额/公司储值卡余额）
  → 商家接单备餐
  → 代表到店取餐
```

**规则**:
- [ ] 代表下单不设截止时间，即选即下
- [ ] 每份餐可标注归属人姓名（方便分发）
- [ ] 支持从"常点模板"快速填充（按用户存储，每个代表下单人各自保存自己上次的菜品组合，非跨用户共享）
- [ ] 支持使用公司储值卡余额支付

**验收标准**（3.4 团体订餐整体）：
- [ ] 拼单：创建团单→分享卡片→多人加入各自选餐支付→截单→合并生成主订单→商家接收，全流程通畅。
- [ ] 代表下单：选择模式→为多人选餐→统一支付→商家接收，全流程通畅。
- [ ] 拼单 A 模式：已支付子订单合并，未支付自动取消并恢复库存。
- [ ] 拼单 B 模式：任一失败全员退款，团单取消。
- [ ] 团单独立退款：参与者 A 退款不影响 B/C/D 的订单，退款金额按子订单独立计算。
- [ ] 部分出餐：商家勾选已完成餐品标记"部分可取"，其余正常流程。

### 3.5 预充值（P1）

**需求**: 采用储值卡/礼品卡模式，支持公司和个人的预充值，用于订单支付。

- [ ] **充值入口**: 小程序"我的"→"我的储值卡"→"购买"
- [ ] **购买方式**: 微信支付购买固定面额储值卡（商家管理后台配置面额档位，如 100/200/500/1000）
- [ ] **公司储值卡**: 公司可申请开通企业账户 → 管理员购买储值卡 → 员工下单时可选"公司账户支付"
- [ ] **个人储值卡**: 个人购买 → 个人下单时可选"余额支付"
- [ ] **余额明细**: 展示购买记录、消费记录、退款入账
- [ ] **余额提醒**: 余额低于设定阈值时，下单时提醒充值

> **合规说明**: 采用储值卡模式而非资金池模式，用户购买的是固定面额的预付卡，资金流为"用户→商户"的货款预付，不涉及二清风险。后续若业务量增大，可对接持牌支付机构的分账系统。

**验收标准**：
- [ ] 微信支付购买储值卡后，余额实时到账。
- [ ] 下单时可选"个人余额"或"公司储值卡"支付，余额不足时提示差额。
- [ ] 余额明细正确展示购买/消费/退款三条流水。
- [ ] 公司管理员可为员工开通公司储值卡使用权限。

### 3.6 折扣引擎（P1）

**需求**: 商家可配置灵活的折扣规则。

**规则条件支持**:
- [ ] 订单金额满足条件（满 X 元）
- [ ] 订单份数满足条件（满 X 份）
- [ ] 指定品类（如"所有饮品"）
- [ ] 指定菜品（如"红烧肉套餐"）
- [ ] 指定时段（工作日午餐 11:00-13:00）
- [ ] 首次下单用户（判定：该 userId 在当前租户下历史"已支付"且"未退款"订单数 = 0）
- [ ] 团单专属

**规则动作支持**:
- [ ] 打折（9 折 / 8.5 折）
- [ ] 减钱（满 100 减 10）
- [ ] 赠送积分（满 50 送 100 积分）
- [ ] 免配送费（仅当 `delivery` 模块激活时可用）
- [ ] 赠送菜品（满 10 份送 1 份）。赠品自动加入订单（默认规格），消耗赠品 SKU 库存。商家可指定哪些菜品可作为赠品，若不指定则从同品类中随机选择最低价商品

**叠加规则**:
- [ ] 每条规则可设置"是否可叠加"
- [ ] 可叠加时按优先级排序（优先级数字越大越先计算）

**验收标准**：
- [ ] 创建满减规则后，符合条件的订单自动应用折扣。
- [ ] 多条可叠加规则按优先级顺序依次计算，不可叠加规则仅取优先级最高的一条。
- [ ] 指定时段规则在非生效时段不触发。
- [ ] "赠送积分"动作正确写入积分流水。

### 3.7 积分系统（P1）

**需求**: 消费积分和积分兑换。

**积分获取**:
- [ ] 消费积分：每消费 N 元 = M 积分（比例商家可配置）
- [ ] 签到积分：每日签到奖励（连续签到递增）。签到重置时间按商家所在时区（BrandConfig 中设置）的凌晨 0:00
- [ ] 分享奖励：分享小程序/团单给好友获得积分

**积分消耗**:
- [ ] 积分抵现：N 积分 = 1 元（兑换比例商家可配置，可设最低抵扣门槛）
- [ ] 积分兑换商品（商家在后台设置兑换商品和所需积分）。兑换后自动生成一个 ¥0 订单（消耗商品库存），随用户下一次到店取餐时一并领取。用户可在"我的-积分-兑换记录"中查看兑换商品和领取状态
- [ ] 积分兑换优惠券

**积分管理**:
- [ ] 积分有效期（商家可设置，如获得后 6 个月有效）
- [ ] 积分明细（获取记录、消耗记录）

**验收标准**：
- [ ] 支付完成后，按商家设定比例自动发放积分。
- [ ] 积分抵现时正确扣减积分，抵现金额准确。
- [ ] 过期积分在每日凌晨自动清零，流水记录为"过期"。
- [ ] 积分兑换商品/优惠券后库存正确扣减。

### 3.8 优惠券（P1）

**需求**: 商家可创建和发放优惠券。

**优惠券类型**:
- [ ] 满减券：满 X 减 Y
- [ ] 折扣券：打 N 折，最高减 Y 元
- [ ] 商品券：免费兑换指定商品。结算时选择商品券 → 对应商品自动以 ¥0 加入订单（消耗该商品 SKU 库存）→ 不可与其他同品类优惠叠加

**发放方式**:
- [ ] 系统发放：新用户注册自动发放
- [ ] 活动发放：商家生成领取链接/二维码
- [ ] 积分兑换：用户用积分兑换优惠券

**使用规则**:
- [ ] 有效期：领取后 N 天有效 / 固定日期范围
- [ ] 使用门槛：最低消费金额
- [ ] 适用范围：全部商品 / 指定品类 / 指定商品
- [ ] 是否可与其他优惠叠加

**验收标准**：
- [ ] 新用户注册后自动收到配置的新人优惠券。
- [ ] 结算页自动匹配最优优惠券，优惠金额计算正确。
- [ ] 优惠券使用后状态变为"已使用"，不可重复使用。
- [ ] 过期优惠券自动失效。

### 3.11 商家管理后台（P0）

**需求**: Web 管理后台，商家管理日常运营。

#### 3.11.1 数据看板
- [ ] 今日营收、今日订单数、今日客单价（"今日"按自然日 00:00 至当前时刻。若商家跨凌晨营业，仍按自然日统计，跨天订单计入下单日）
- [ ] 近 7 天营收趋势图
- [ ] 热门菜品 Top 10
- [ ] 待处理订单数（醒目提醒）
- [ ] **日对账**：展示当日系统订单总额 vs 微信支付结算额。差额 > 0 标记异常（可能原因：未到账/退款/手续费差异），支持查看明细清单

> **模块边界说明**：基础看板（3.11.1）展示**今日实时数据 + 近 7 天趋势**，免费包含在 `base` 模块中。`advanced-stats` 模块（付费）提供品类分析、时段分析、同比环比、用户画像等多维历史数据分析。

#### 3.11.2 菜品管理
- [ ] 分类管理（新增/编辑/删除分类、排序）
- [ ] 菜品 CRUD（名称、图片、价格、描述、规格、库存、**单位**、上架/下架）。单位选项：份/碗/杯/个/笼/瓶/盒，默认"份"。展示格式如"¥18.00/份"。每个菜品 **1 张主图**（必填，用于列表缩略图）+ **最多 5 张详情图**（可选，用于详情页轮播）
- [ ] **手动估清**：店员/厨师可手动将菜品标记为"今日估清"（区别于库存自动售罄）。估清后前端显示"今日已售罄"，不影响库存数字。关店时所有估清标记自动清除。适合"食材不够但不想改库存"的实际场景
- [ ] **数量上限**：单个商家菜品 ≤ 500 道（不含 SKU 展开），分类 ≤ 30 个。超出提示"已达上限"
- [ ] 批量上下架
- [ ] 菜品定时上下架（周三特价菜自动上架）
- [ ] 批量导入/导出：CSV 格式，列=菜品名称/分类/价格/描述/库存。管理后台提供模板文件下载。导入时逐行校验，错误行跳过并给出错误报告。

#### 3.11.2.1 菜品规格联动与菜单维护
- [ ] **规格售罄联动**：某规格（如"大份"）售罄时，菜品仍可点其他规格（如"小份"），售罄规格在前端置灰不可选。
- [ ] **分类删除保护**：分类下有菜品时不可删除，需先将菜品转移或下架。
- [ ] **菜品快照机制**：订单生成时，将当前菜品名称、规格、价格、图片URL等完整保存到订单明细中，后续商家修改菜品不影响历史订单展示。图片额外保存缩略图 base64（≤10KB），防止原图被删后历史订单无法展示菜品图
- [ ] **定时上下架**：支持设置菜品在特定日期/时段自动上架或下架。
- [ ] **菜品图片上传**：调用统一上传接口（见 3.17），返回 URL 后自动填入表单。
- [ ] **SKU 数量限制**：为防止笛卡尔积爆炸，规格组 ≤ 3 个，每组选项 ≤ 5 个，单个菜品总 SKU ≤ 50。超出时提示商家拆分菜品或减少规格维度。
- [ ] **规格模板修改规则**：规格模板修改不影响已创建的菜品（菜品创建时复制模板内容为独立副本）。修改模板仅影响后续通过该模板新创建的菜品

#### 3.11.3 订单管理

### 3.16 支付安全增强

- [ ] **支付回调幂等性**：微信支付通知回调使用 `transaction_id` 或 `out_trade_no` 做幂等校验，重复回调不重复更新订单状态。
- [ ] **支付超时与回调的并发防护**：定时任务取消"待支付"订单前，先查询微信订单接口确认支付状态，避免"支付刚成功但回调排队中"时误取消。使用乐观锁（version 字段）更新订单状态。
- [ ] **大额支付风控**：单笔订单金额超过 ¥5,000 时，前端弹窗二次确认；管理后台可配置风控阈值和是否开启。
- [ ] **接口限流细化**：下单接口对同一用户/IP 限制频率（每秒不超过 5 次），防止误触或恶意刷单。
- [ ] **支付服务降级**：微信支付接口超时或返回系统错误时，订单保持"待支付"状态（不自动取消），用户可稍后继续支付。用户支付时网络断开返回订单页后，订单详情展示"查看支付结果"按钮，主动调用微信订单查询接口确认
- [ ] **微信审核合规**：
  - 小程序服务类目必须为「餐饮服务」（非「生活服务」）以支持储值卡功能
  - 储值卡页面禁止出现"投资""理财""返利""提现"等字样，余额不可提现、不可转赠
  - 分享奖励积分改为"分享后好友下单可获得积分"（非"分享即得"，避免微信诱导分享规则）
- [ ] **防刷机制**：
  - 分享积分：同一设备/IP 的新用户下单不计入分享奖励。每用户每自然月通过分享获得积分上限 500 分（商家可配）
  - 优惠券：同一用户对同一优惠券模板最多领取 1 次（系统发放类）。活动领取类同一 IP 每小时最多领取 3 张券

### 3.17 图床与文件存储

**需求**：统一管理系统中所有图片和文件的上传、存储、访问，兼容 SaaS 托管和源码自部署两种模式。

#### 3.17.1 存储架构

| 模式 | 默认方案 | 说明 |
|---|---|---|
| **SaaS 托管** | 阿里云 OSS / 腾讯云 COS（选一） | 按租户分目录隔离，统一 CDN 加速 |
| **源码交付** | 本地磁盘存储 | 上传至服务器 `/uploads` 目录，通过 Nginx 静态文件服务访问，商家可自行替换为 OSS |

#### 3.17.2 SaaS 模式要求

- [ ] **多租户隔离**：每个商家在 OSS Bucket 下有独立目录（如 `/{tenant_id}/`），上传接口自动根据当前租户 ID 写入对应目录。
- [ ] **访问控制**：菜品图片等公开资源设置为公共读；用户上传的认证材料等敏感文件设置为私有，通过签名 URL 访问。
- [ ] **CDN 加速**：公开资源绑定 CDN 域名，图片 URL 返回 CDN 地址而非 OSS 直连地址。
- [ ] **图片处理**：上传时自动压缩（如 800px 宽 + 质量 80%），生成缩略图用于列表展示，减少带宽消耗。
- [ ] **格式校验**：仅允许 jpg、jpeg、png、gif、webp 格式。
- [ ] **大小限制**：单张图片 ≤ 5MB，Banner ≤ 2MB。
- [ ] **上传频率限制**：同一租户每秒 ≤ 10 次上传请求。

#### 3.17.3 源码交付模式要求

- [ ] **默认本地存储**：交付包内置本地存储方案，上传接口将文件写入服务器 `{项目根目录}/uploads/` 目录。
- [ ] **静态访问**：Nginx 配置模板包含 `/uploads/` 路径的静态文件服务规则，图片通过 `https://商家域名/uploads/xxx.jpg` 直接访问。
- [ ] **扩展接口**：后端文件存储模块提供抽象接口（`FileStorageService`），商家二开时可实现 `upload()`、`delete()`、`getUrl()` 三个方法对接自己的 OSS。
- [ ] **部署文档说明**：明确本地存储的磁盘规划建议（预估每日新增图片量 × 保留天数）、备份策略、以及如何迁移到 OSS。
- [ ] **目录结构**：本地存储按日期分目录（如 `/uploads/2026/06/16/`），避免单目录文件过多。

#### 3.17.4 上传接口设计

- [ ] **统一上传接口**：`POST /api/upload`，支持单文件和批量（最多 9 张）。
- [ ] **返回格式**：上传成功后返回文件 URL 或 fileId，前端可直接用于展示或提交到菜品/Banner 表单。
- [ ] **文件去重**：相同 MD5 的文件不重复存储，返回已有 URL。
- [ ] **垃圾回收**：管理后台删除菜品/Banner 时，对应图片同步删除（或标记删除，定时清理）。

#### 3.17.5 管理后台图片管理（可选，P2）

- [ ] **素材库**：商家可在管理后台查看已上传的所有图片，支持预览、删除、按时间筛选。
- [ ] **使用情况追踪**：每张图片显示被哪些菜品/Banner 引用，防止误删。

**验收标准**：
- [ ] SaaS 模式下，不同商家上传的图片在 OSS 中目录隔离，A 商家无法访问 B 商家的图片。
- [ ] 源码交付模式下，默认本地存储开箱即用，部署后即可上传和展示图片。
- [ ] 上传接口格式校验生效，上传非图片文件被拒绝并返回明确错误提示。
- [ ] 大图片自动压缩，缩略图在列表页正常展示，原图在详情页按需加载。

### 3.19 场景化运营工具（P1）

> 参考瑞幸"场景化品类"和美团"智能推荐"的运营思路，为商家提供轻量级运营工具。不与大厂拼算法，而是提供**商家可手动配置**的场景化能力。

#### 3.19.1 菜品分类标签

**需求**：菜品分类支持标签装饰，让菜单不仅仅是分类，而是融合促销和场景的运营入口。

- [ ] **标签类型**：
  - `新品` — 新品推荐（绿色标签）
  - `人气Top` — 销量排行前 N 自动标记（橙色标签）
  - `限时优惠` — 参与折扣活动的菜品（红色标签）
  - `时令推荐` — 季节性菜品（蓝色标签）
  - `售罄` — 库存为 0 自动标记（灰色标签）
- [ ] **标签配置**：商家在管理后台手动设置标签类型，`人气Top` 和 `售罄` 由系统自动计算
- [ ] **标签展示**：菜品卡片左上角角标，不超过 2 个标签（取优先级高的）

#### 3.19.2 菜品搭售推荐

**需求**：商家可为菜品设置关联推荐，下单时展示搭配商品，提升客单价。

- [ ] **配置方式**：管理后台菜品编辑页 → 「关联推荐」→ 选择 1-5 个关联菜品
- [ ] **展示位置**：
  - 菜品详情页底部「搭配推荐」区域
  - 购物车抽屉面板底部「再加一份？」
- [ ] **推荐逻辑**：纯人工配置，V1.0 不做算法推荐
- [ ] **加购交互**：推荐菜品旁显示 [+] 按钮，一键加入购物车（不跳页）

#### 3.19.3 优惠券智能匹配

**需求**：结算页自动匹配最优优惠券，降低用户选择成本。

**计算顺序**（全优惠叠加统一公式）：
```
订单原价 → 应用折扣规则（满减/打折/赠品）→ 折扣后金额
→ 应用优惠券（满减券/折扣券/商品券）→ 券后金额
→ 应用积分抵现（若用户选择）→ 最终支付金额
→ 微信支付/余额支付补足
```

- [ ] **自动匹配**：结算页根据折扣后订单金额和商品品类，自动匹配可用优惠券中优惠力度最大的一张
- [ ] **手动切换**：用户可以点击优惠券区域展开所有可用券列表，手动切换
- [ ] **不可用券展示**：展示不可用券并标注不满足的条件（如"还差 ¥12.5"），引导凑单
- [ ] **凑单提示**：当用户离优惠门槛差距较小时（如差 ≤¥5），提示"再加 ¥X 即可享 Y 优惠"

#### 3.19.4 常点清单

**需求**：自动聚合用户历史高频订单，减少重复选餐时间。

- [ ] **计算规则**：统计用户近 30 天内下单 ≥ 3 次的菜品，按频次降序排列
- [ ] **展示位置**：首页「常点清单」瓷片区、下单时「常点模板」快捷入口
- [ ] **一键复购**：点击常点清单中的菜品直接加入购物车

**验收标准**（3.19 整体）：
- [ ] 菜品标签在菜单页正确展示，优先级逻辑生效（不超过 2 个）。
- [ ] 搭售推荐菜品在详情页和购物车抽屉正确展示，[+] 按钮可一键加购。
- [ ] 结算页自动匹配最优优惠券，用户可手动切换并实时看到价格变化。
- [ ] 常点清单准确反映近 30 天下单 ≥ 3 次的菜品。

### 3.20 商家入驻与激活流程（P0）

**需求**：定义商家从签约到小程序上线的完整流程。

```
商家签约（线下），提交审核材料：

  → 系统自动生成初始管理员账号（老板角色），密码通过短信/邮件发送
  → 商家登录管理后台 → 首次登录强制修改密码
  → 引导完成初始设置：
      ① 上传Logo和Banner

  → 小程序端同步生效
```

**初始状态定义**：
- [ ] 新 Tenant 创建后，菜单为空（无分类、无菜品）

- [ ] P端创建 Tenant 后，商家可立即登录管理后台。
- [ ] 首次登录引导流程完整，商家可在 10 分钟内完成基础设置。
- [ ] 商家添加首个菜品后，小程序端自动从"筹备中"切换为正常菜单。
- [ ] **小程序版本管理**：使用微信原生版本管理——开发版（内部开发测试）→ 体验版（商家验收确认）→ 提交微信审核 → 审核通过后发布正式版。模板升级时先更新开发版 → 商家验收体验版 → 提交审核 → 发布

## 4. 非功能需求

### 4.1 性能
- [ ] 小程序首页加载时间 < 2 秒
- [ ] 菜品列表接口响应时间 < 200ms
- [ ] 支持单个商家峰值 500 QPS（午餐高峰）

### 4.2 安全
- [ ] 所有 API 通过 HTTPS
- [ ] JWT Token 过期时间 24h，支持 refresh。小程序端：API 返回 401 时自动调用 `wx.login` 获取新 code → 后端换取新 JWT → 静默续期，用户无感知。refresh token 过期（7天）则跳转登录页
- [ ] 商家管理后台强制密码强度（8 位以上，含大小写+数字）。登录失败 5 次锁定 15 分钟，锁定期间可通过"忘记密码"重置（手机验证码验证）自动解锁。P端管理员可手动解锁账号
- [ ] 微信支付回调验签
- [ ] 微信支付回调幂等处理
- [ ] 接口限流（防止刷单，下单接口同一用户/IP ≤ 5次/秒）
- [ ] SQL 注入防护（ORM 参数化查询）
- [ ] 大额支付二次确认（阈值可配，默认 ¥5,000）
- [ ] **管理后台会话**：使用 JWT，存储在 localStorage，过期时间 12h。登出时清除 token
- [ ] **CORS 策略**：API 仅允许已配置的域名跨域（管理后台域名 + 小程序合法域名），生产环境禁止 `*`
- [ ] **CSRF 防护**：管理后台状态变更操作需在请求头携带 `X-Requested-With: XMLHttpRequest`，后端校验
- [ ] **文件上传校验**：上传时校验文件头魔数（magic bytes）确认实际格式，拒绝伪造扩展名（如把 .exe 改为 .jpg）

### 4.3 可用性
- [ ] 服务可用性 ≥ 99.5%
- [ ] 数据库每日自动备份（保留最近 30 天）
- [ ] 备份恢复演练每季度一次（验证备份可恢复性）
- [ ] 核心接口异常告警（响应时间 > 2s 或错误率 > 1%）

### 4.4 兼容性
- [ ] 微信小程序基础库 ≥ 2.10.0
- [ ] iOS 12+、Android 7+
- [ ] 管理后台支持 Chrome 80+、Edge 80+
- [ ] uni-app 编译后主包 ≤ 1.5MB（微信限制 2MB，留余量），总包 ≤ 8MB（V1.0）。使用分包加载：主包=首页+菜单，分包=订单/团单/个人中心
- [ ] **订单状态实时更新**：订单详情页每 10 秒轮询订单状态接口（微信小程序不支持 WebSocket 长连接），状态变更时重新拉取完整时间轴数据

### 4.5 可维护性
- [ ] 代码覆盖率 ≥ 70%（后端非核心模块）
- [ ] 每个模块有独立的 README
- [ ] 数据库 Migration 脚本管理
- [ ] 交付包提供部署文档和二开文档
- [ ] **API 分页标准**：所有列表类接口默认 `pageSize=20`，最大 `pageSize=100`。使用 `page` + `pageSize` 分页。响应含 `total`（总数）和 `hasMore`（是否还有更多）。订单列表按创建时间倒序
- [ ] **开发环境**：小程序使用微信开发者工具 + 测试号 AppID。正式联调需商家提供已通过类目审核的 AppID。后端提供 Docker Compose 一键启动本地开发环境
- [ ] **支付联调要求**：生产上线前必须完成至少 1 笔真实支付 + 退款的端到端测试（使用测试商户号）
- [ ] **日志规范**：业务操作（订单创建/支付/退款/状态变更）→ INFO 级别；支付异常/回调失败 → ERROR 级别；调试信息 → DEBUG 级别。敏感信息（手机号/openid）需脱敏后记录（如 `138****1234`）。生产环境默认 INFO 级别

#### 5.1.2 市场关键发现

1. **"低代码平台 10 万做一个小程序"不属实**：低代码平台年费集中在 ¥698-26,800。¥100,000 是外包公司全定制开发的中间档位报价，非低代码平台收费。用户可能混淆了交付模式或将打包总价（软件+硬件+部署+定制）归为单一收费。
2. **我们的差异化市场空白**：市面上无人同时提供 SaaS 租用 + 源码买断两种模式。SaaS 平台不卖源码（除即速应用支持导出），外包公司不做 SaaS 年费。我们跨两种交付形态是核心竞争壁垒。
3. **团餐场景是竞品盲区**：凡科/有赞/微盟/美团/客如云均无团单拼单+代表下单的原生支持。写字楼午餐团餐场景是未被充分服务的细分市场。
4. **源码保护机制独一无二**：市面上成品源码交付无代码保护（买家可阅读、修改、转卖全部源码）。我们的 .node 核心编译 + 模块物理删除 + 水印溯源机制在市场上没有等价物，这为源码交付提供了溢价基础。

```
销售话术："您已经付了 ¥27,000 的 SaaS 年费，再加 ¥12,800 就能永久买断源码，
```

## 6. 术语表

| 术语 | 定义 |
|---|---|
| **租户 (Tenant)** | 一个使用我们模板的商家，拥有独立的小程序 appId 和数据空间 |
| **模块 (Module)** | 一个可独立购买和启用的业务功能单元 |
| **团单 (Group Order)** | 多人参与的团体订餐订单 |
| **拼单 (Pool)** | 团单模式之一，多人各自选餐支付，系统合并为一个团单 |
| **代表下单 (Represent)** | 团单模式之一，一人统一为团队选餐支付 |
| **截单** | 拼单截止，锁定所有参与者订单，合并提交给商家 |
| **模板 (Template)** | 我们开发的完整功能源码，包含所有模块和配置系统 |
| **交付包 (Delivery Package)** | 经过预处理的源码，给到某个具体商家，只包含其购买的模块 |
| **水印 (Watermark)** | 注入到交付源码中的隐形商家标识，用于溯源 |
| **平台** | 指我们——模板开发方和 SaaS 运营方 |
| **储值卡** | 用户用微信支付购买的固定面额预付卡，用于订单支付，非资金池模式 |
| **.node 模块** | Node.js 原生二进制扩展，用于封装核心逻辑，源码不可见 |

## 8. 已确认决策汇总

> 以下事项已逐项讨论并确认，作为开发基准。

### 8.1 堂食点餐（P2，V1.0 仅定义，V2.0 实现）

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 桌号状态流转 | 空闲 → 占用（首人扫码绑定）→ 已结账待清 → 空闲。多人扫码自动加入同一桌 |
| 2 | 加菜逻辑 | 追加到已有订单组，新增菜品需重新支付 |
| 3 | 催菜与出餐 | 厨师端 + 服务员端都通知。服务员端有待送餐列表（按桌号排序） |
| 4 | 结账流程 | 混合模式：用户可自助支付也可叫服务员结账。支付后自动变"已结账待清"，服务员清桌后改"空闲" |
| 5 | 服务员端功能 | 完整功能：各桌概览、待送餐列表、催菜提醒、结账操作、清桌操作、加菜协助 |
| 6 | 桌号二维码 | 固定二维码，码内包含桌号 ID |
| **范围** | **V1.0 不做堂食模块，完整设计保留在 PRD 中供 V2.0 实现** | |

### 8.2 支付流程

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 余额不足处理 | 不支持组合支付。余额不足提示差额，引导选微信支付或先充值 |
| 2 | 退款路径 | 原路退回：余额支付的退余额，微信支付的退微信 |
| 3 | 储值卡有效期 | 无有效期，余额永久有效 |
| 4 | 支付回调异常 | 回调验签通过但订单已取消 → 自动发起退款。金额不一致以微信回调为准 + 记录异常日志告警 |
| 5 | 回调丢失兜底 | 定时任务每分钟查询过去 5 分钟内"待支付"订单，调用微信订单查询接口。最多查 30 分钟 |
| 6 | 团单多支付方式 | 各付各的：参与者各自选择支付方式，互不影响 |

### 8.3 团单合并后生命周期

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 部分退款 | 支持独立退款：参与者 A 可以单独退，不影响 B/C/D。退款按子订单独立计算 |
| 2 | 取餐号 | 一个团单一个主号 + 每人独立子编号（方便按人分发和各自取餐） |
| 3 | 部分出餐 | 支持：商家勾选已完成的餐品 → 标记"部分可取" → 通知取餐人 |
| 4 | 再来一单 | 重新发起拼单：复制菜品和设置，模式与上次一致 |

### 8.4 权限模型

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 老板 vs 店长 | 老板可以兼任店长。老板独有：退款审批、模块购买/续费、员工管理/角色分配、完整财务报表、营业设置修改。店长管日常运营（订单/菜品），不碰钱和人 |
| 2 | 操作权限拆分 | 拆分为独立权限点：确认接单、取消订单、退款审批、修改订单。不同角色分配不同组合 |
| 3 | 多店场景 | 一个账号切换多店，V1.0 做。数据完全隔离 |
| 4 | P 端数据访问 | 日常只看聚合大盘。客诉时通过后台输入订单号查询单个订单详情（白盒操作，记录审计日志） |

### 8.5 菜品规格系统

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 规格与价格 | SKU 模式：每个规格组合 = 独立 SKU，独立价格和库存 |
| 2 | 多级规格 | 笛卡尔积 SKU：辣度 3 种 × 份量 3 种 = 9 个 SKU |
| 3 | 规格与库存 | 分开库存：每个 SKU 独立库存计数，售罄互不影响 |
| 4 | 规格模板 | 支持：商家创建规格模板（名称 + 选项列表），复用到多个菜品 |
| 5 | 加料归属 | 作为规格选项，纳入 SKU 笛卡尔积 |

### 8.6 消息推送

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 消息触发条件 | 备餐完成通知 = 商家点击"完成备餐"时触发。先记好 5 个消息场景（下单成功/备餐完成/取餐提醒/退款到账/截单通知），开发时去微信后台申请模板 ID |
| 2 | 模板字段映射 | 先记录场景，开发阶段再申请模板 ID 并做字段映射 |

### 8.7 商家端订单操作

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 批量接单 | 需要：订单列表顶部"一键确认全部待接单"按钮 |
| 2 | 取消原因 | 必选原因：菜品售罄 → 自动恢复库存；用户要求 → 不恢复库存；无法配送/其他 |
| 3 | 订单修改 | 仅可改备注，不能增减菜品或改价 |
| 4 | 订单标签 | 支持预设标签：加急/过敏/特殊备注/团单勿混。订单列表可筛选 |

### 8.8 积分抵现支付

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 组合支付 | 积分 + 微信组合支付，先扣积分抵现部分 → 微信支付剩余 |
| 2 | 退款路径 | 积分退积分、微信退微信，原路返回 |

### 8.9 源码交付验证与责任

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 冒烟测试 | 提供冒烟脚本。商家先跑冒烟 → 冒烟不过且环境正确 → 我们远程排查。冒烟通过但商家自己改了的 → 不在免费支持范围 |
| 2 | 水印溯源 | 多层水印（代码 + 二进制 + 图片 + 字符串）。诚实告知"交付包内有唯一标识用于版权保护"。即使浅层被洗，二进制隐写和图片隐写难以完全清除 |

### 8.10 跨模块优惠计算

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 团单 + 折扣 | 各自独立计算：折扣按每人子订单独立计，满减门槛各自满足 |
| 2 | 团单 + 积分 | 各自获得：参与者按自己实付金额独立计算积分 |
| 3 | 团单 + 支付 | 各付各的：参与者各自选择支付方式（微信/余额/公司储值卡） |
| 4 | 折扣 + 优惠券 | 折扣先计算 → 折扣后金额再应用优惠券。同类型优惠按优先级排序 |
| 5 | 积分 + 微信组合 | 先扣积分抵现，不足部分微信补足 |
