## 1. Spec 的本质

### 1.1 定义

**Spec = 在信息交接面上放置的、可验证的、版本化的信息契约。**

三层含义：

| 层次 | 含义 | 反例 |
|------|------|------|
| **信息契约** | 两个角色之间对"什么是对"的共同约定 | "代码就是这样写的"——代码是行为不是契约 |
| **可验证** | 每条陈述都能通过某种方式判断实现是否满足 | "系统应该快速响应"——不可验证 |
| **版本化** | 变更可追溯，新旧版本可对比 | 口头约定——变更无记录 |

### 1.2 Spec 不是"描述软件的文字"

Spec 是**边界对象（Boundary Object）**——连接不同认知世界的翻译层：

```
业务方的认知世界                    开发者的认知世界
（用户场景、商业价值）              （数据结构、算法、状态迁移）
        \                               /
         \                             /
          ┌───────────────────────────┐
          │        Spec（翻译层）      │
          │  用双方都能精确理解的语言   │
          │  定义"什么是对"            │
          └───────────────────────────┘
```

**Spec 的质量不由"写得多详细"衡量，而由"消除了多少歧义"衡量。**

### 1.3 Spec 作为信息压缩

```
现实世界的复杂性（无限维度）
        ↓ Spec = 有限维度的抽象（提取关键约束）
    Spec 文档
        ↓ 实现 = 将抽象还原为具体
   代码实现
```

一份好的 Spec 做两件事：
- **压缩**：从无限细节中提取出关键约束
- **可还原**：不同读者能独立还原出相同理解

如果两个开发者读同一份 API-SPEC 写出的接口返回了不同格式，这份 Spec 就失败了——它的"还原歧义"太高。

## 2. Spec 分类体系

### 2.1 四维分类矩阵

从四个正交维度对任何 Spec 进行分类：

| 维度 | 问题 | 可选值 |
|------|------|--------|
| **生命周期阶段** | 在哪个阶段产生？ | 需求 → 设计 → 实现 → 测试 → 交付 → 运维 |
| **读者对象** | 给谁读？ | 人类（PM/开发/测试/运维）vs 机器（Agent/CI） |
| **抽象层级** | 离业务多近？ | 业务层 → 逻辑层 → 物理层 → 元层 |
| **变更频率** | 多久改一次？ | 稳定（架构决策）→ 中频（API 端点）→ 高频（测试用例） |

### 2.2 按层次的五层模型

```
┌──────────────────────────────────────────────┐
│ 元层（Meta-Spec）                             │
│ 定义 Spec 本身的规则：格式、命名、引用规范      │
│ 例：SPEC.md（导航索引）、CLAUDE.md（Harness 规则）│
├──────────────────────────────────────────────┤
│ 语义层（Semantic Specs）                      │
│ 描述"是什么"和"为什么"                        │
│ 例：PRD、V1-SCOPE、ARCHITECTURE、MODULES      │
├──────────────────────────────────────────────┤
│ 结构层（Structural Specs）                    │
│ 描述"怎么组织"和"边界在哪"                     │
│ 例：DATA-MODEL、API-SPEC                      │
├──────────────────────────────────────────────┤
│ 行为层（Behavioral Specs）                    │
│ 描述"怎么运转"和"什么规则"                     │
│ 例：STATE-MACHINES、BUSINESS-RULES            │
├──────────────────────────────────────────────┤
│ 验证层（Verification Specs）                  │
│ 描述"怎么确认对"                              │
│ 例：QA-TEST-SPEC、AGENTIC-TEST-SPEC           │
└──────────────────────────────────────────────┘
```

### 2.3 完整 Spec 矩阵（33 类）

按生命周期阶段展开的完整 Spec 清单。使用方法是：在项目动手前，逐行检查是否需要该 Spec。

#### 需求层

| # | Spec | 触发条件 | 交接面 | 最小内容 |
|:-:|------|---------|--------|---------|
| R1 | 产品需求文档（PRD） | 任何超过 1 周的项目 | PM → 全体 | 用户角色、功能清单（按优先级）、非功能需求、术语表 |
| R2 | 用户故事/用例地图 | 多角色多场景 | PM → 设计+开发 | 每个角色的完整操作路径、异常路径 |
| R3 | 功能范围清单 | 有分期交付计划 | PM → 开发+测试 | V1/V2 明确边界、"不做"的清单 |
| R4 | 业务指标定义 | 有数据指标需求 | PM → 开发 | 指标公式、数据来源、计算周期 |
| R5 | 竞品/参考分析 | 新产品/新市场 | PM → 设计 | 竞品功能对比、差异点 |

#### 设计层

| # | Spec | 触发条件 | 交接面 | 最小内容 | 自动化 |
|:-:|------|---------|--------|---------|:-----:|
| D1 | 系统架构文档 | 多服务/多端/多租户 | 架构师 → 开发 | 拓扑图、技术选型及理由、ADR、外部依赖 | 10% |
| D2 | 模块/服务边界定义 | 模块数 > 5 | 架构师 → 开发 | 模块清单、接口边界、依赖关系、权限矩阵 | 30% |
| D3 | 数据模型文档 | 表数 > 5 | 后端 → 全体 | ER 图、表清单及字段、索引策略 | 80% |
| D4 | API 契约文档 | 前后端分离 | 后端 → 前端+测试 | 端点、参数、响应格式、错误码、认证方式 | 80% |
| D5 | 状态机文档 | 有状态流转的核心实体 | 后端 → 测试 | 状态图、迁移规则、触发条件、并发控制 | 20% |
| D6 | 业务规则文档 | 有复杂计算/判断逻辑 | 业务方 → 开发+测试 | 计算顺序、边界条件、异常处理、示例演算 | 5% |
| D7 | UI/交互设计文档 | 有用户界面 | 设计 → 前端 | 页面结构、组件状态（空/加载/错误/成功） | 0% |
| D8 | 消息/事件契约 | 有异步通信 | 生产者 → 消费者 | 事件类型、payload schema、触发条件、消费语义 | 70% |
| D9 | 配置项文档 | 配置项 > 10 | 开发 → 运维 | 配置项名、默认值、取值范围、生效方式 | 60% |

#### 实现层

| # | Spec | 触发条件 | 交接面 | 最小内容 |
|:-:|------|---------|--------|---------|
| I1 | 编码规范 | 多人协作 | TL → 全体开发 | 命名约定、目录结构、注释规范、禁止模式 |
| I2 | 依赖清单 | 外部依赖 > 5 | 开发 → 运维+安全 | 库名、版本、用途、许可证、漏洞等级 |
| I3 | 错误处理规范 | API > 10 | 后端 → 前端 | 错误码体系、HTTP 状态码映射 |
| I4 | 日志/监控埋点规范 | 生产环境 | 开发 → 运维 | 日志级别、关键埋点位置、日志格式 |

#### 测试层

| # | Spec | 触发条件 | 交接面 | 最小内容 | 自动化 |
|:-:|------|---------|--------|---------|:-----:|
| T1 | 测试策略文档 | 正式项目 | QA → 全体 | 测试层次、覆盖目标、环境配置 | 10% |
| T2 | QA 测试说明书 | 有专职 QA | QA → 开发+PM | 用例清单（步骤+预期）、优先级 | 20% |
| T3 | Agent 可执行测试书 | 使用 AI Agent 测试 | Agent → CI | curl 指令、JSONPath 断言、变量传递、依赖 DAG | 50% |
| T4 | 性能基准文档 | 有性能要求 | 开发 → QA | 关键接口、目标 QPS/P95、压测场景 | 0% |
| T5 | 安全测试清单 | 涉及支付/个人信息 | 安全 → 开发 | OWASP Top 10、认证/授权/加密检查项 | 30% |

|:-:|------|---------|--------|---------|

|:-:|------|---------|--------|---------|

## 3. Spec 的生命周期

### 3.1 生成时机

每一类 Spec 应该在什么时间点产生？谁来负责？不产生的后果是什么？

```
签约 ──→ 需求评审 ──→ 架构设计 ──→ 数据库设计 ──→ 接口设计
  │         │           │            │              │
  │    PRD.md(草稿)  ARCHITECTURE  DATA-MODEL    API-SPEC
  │    V1-SCOPE      .md(初稿)     .md(草稿)     .md(草稿)
  │                  MODULES.md   STATE-MACHINES
  │                               .md(草稿)
  │                               BUSINESS-RULES
  │                               .md(草稿)
  │         │           │            │              │
  │    PRD.md(封板)     │            │              ├─ 编码 ────→ 单元测试 ────→ 联调
  │    V1-SCOPE(锁定)   │            │              │               │              │
  │                     │            │          API-SPEC       AGENTIC-TEST    API-SPEC
  │                     │            │          .md(稳定)      -SPEC.md        .md(修正)
  │                     │            │                         (首次生成)       │
  │                     │            │                                         │
  │                     │            │              ├─ E2E 测试 ────→ 发版
  │                     │            │              │               │
  │                     │            │         QA-TEST-SPEC    AGENTIC-TEST
  │                     │            │         .md(完稿)       -SPEC.md(更新)
  │                     │            │         AGENTIC-TEST    所有 Spec
  │                     │            │         -SPEC.md(完稿)   (归档封板)
```

### 3.2 各阶段的完成度要求

| 时间点 | 产出 | 完成度要求 | 缺失后果 |
|--------|------|-----------|---------|
| 需求评审前 | PRD | 草稿 → 评审通过 | 需求范围无边界，评审会沦为吵架 |
| 架构设计 | ARCHITECTURE + MODULES | 初稿（关键决策必须定） | 技术选型反复，方案迟迟不定 |
| 数据库设计 | DATA-MODEL | 核心实体+关系必须先定 | Migration 反复回滚 |
| 逻辑设计 | STATE-MACHINES + BUSINESS-RULES | 状态+规则必须写下来 | 边界条件凭感觉写 |
| 接口设计 | API-SPEC | 草稿 → 前后端评审对齐 | 联调阶段发现对不上 |
| 编码开始 | 以上全部 | 评审通过 | 边写边改 Spec，Spec 沦为后补文档 |
| 测试阶段 | QA-TEST-SPEC + AGENTIC-TEST-SPEC | 完稿 | 测试覆盖靠感觉 |

### 3.3 关键原则：不要在探索阶段强行 Spec-First

```
探索阶段（需求不稳定、方案未确定）：
  → 代码先行 → Spec 事后提取 → Spec 是"知识沉淀"

收敛阶段（需求冻结、方案确定）：
  → Spec 先行 → 代码从 Spec 生成 → Spec 是"设计工具"
```

## 4. Spec 依赖关系

### 4.1 依赖有向图（DAG）

```
                    PRD.md（需求锚点）
                    /    |     \
                   /     |      \
          V1-SCOPE.md  ARCHITECTURE.md
              \           /    |    \
               \         /     |     \
           MODULES.md    DATA-MODEL.md
                    \      /      \
                     \    /        \
                  API-SPEC.md   STATE-MACHINES.md
                      |   \        /
                      |    \      /
                      |  BUSINESS-RULES.md
                      |       |
                      |       |
                  QA-TEST-SPEC.md
                      |
                AGENTIC-TEST-SPEC.md
```

### 4.2 单向依赖 vs 双向交叉引用

**单向依赖（上游必须先完成）：**

| 依赖方向 | 推导关系 |
|---------|---------|
| PRD → V1-SCOPE | V1 范围从 PRD 功能清单中选取 |
| PRD → STATE-MACHINES | 状态机从 PRD 订单/团单流程提取 |
| PRD → BUSINESS-RULES | 规则从 PRD 非功能需求推导 |
| DATA-MODEL → API-SPEC | API 响应字段映射到表.列 |
| BUSINESS-RULES → QA-TEST-SPEC | 每条业务规则至少对应 1 条测试用例 |
| QA-TEST-SPEC → AGENTIC-TEST-SPEC | Agent 用例从 QA 用例筛选+结构化 |

**双向交叉引用（互相约束，必须同步更新）：**

| 文档对 | 交叉约束关系 |
|--------|------------|
| DATA-MODEL ↔ API-SPEC | 加字段 → API 响应变；新增端点需要新字段 |
| STATE-MACHINES ↔ BUSINESS-RULES | 状态迁移触发规则；规则约束状态迁移合法性 |
| MODULES ↔ ARCHITECTURE | 模块拆分反映架构；架构变更影响模块边界 |

### 4.3 关键路径（最长依赖链）

```
PRD → ARCHITECTURE → DATA-MODEL → API-SPEC → BUSINESS-RULES → QA-TEST-SPEC → AGENTIC-TEST-SPEC
                                                                  （7 跳）
```

PRD 改了订单流程 → 需要依次更新 6 份下游文档。

## 5. Agentic Test Spec

### 5.1 定义

**AGENTIC-TEST-SPEC = QA-TEST-SPEC 的"可执行投影"（Executable Projection）。**

它不是 QA-TEST-SPEC 的子集（减少用例），也不是镜像（换种写法），而是一个**独立的新品类**——面向 Agent 消费者的、机器可解析执行的规格。

### 5.2 与 QA-TEST-SPEC 的本质区别

| 维度 | QA-TEST-SPEC（人读） | AGENTIC-TEST-SPEC（Agent 执行） |
|------|---------------------|-------------------------------|
| 粒度 | 语义级（"验证库存不足返回错误"） | 指令级（`HTTP 409 + .code = "STOCK_INSUFFICIENT"`） |
| 可执行性 | 需要人类理解后转化为操作 | 机器可直接解析执行 |
| 状态管理 | 隐含在段落顺序中 | `depends_on` 显式 DAG |
| 变量传递 | 无 | `{{token}}` → `{{orderId}}` 链式传递 |
| 断言精度 | "应该返回成功" | `status == 200 && .data.orderNo matches /^\d{20}$/` |
| 消费者 | 人类 QA 工程师 | Claude Code Agent / CI Runner |
| 覆盖率 | 全量（~198 条） | 关键路径（40-60 条） |

### 5.3 在 Spec 体系中的位置

```
QA-TEST-SPEC : AGENTIC-TEST-SPEC ≈ 源代码 : 编译产物
```

QA-TEST-SPEC 是人类可读的、语义级的测试描述。
AGENTIC-TEST-SPEC 是从中编译出的、Agent 可执行的测试指令。

两者的关系是**双向追溯**：每条 Agentic 用例标注来源 QA 用例 ID。

### 5.4 设计法则

**法则 1：一个用例只验证一件事。**
失败时需要精确定位，而不是在一个大用例中猜测哪里坏了。

**法则 2：变量是第一公民。**
上一步的结果传给下一步，不靠 Agent 的记忆，靠显式的变量绑定。

**法则 3：断言覆盖"数据形状"和"业务语义"两层。**
只验证 `status == 200` 不够，还要验证返回数据的业务含义是否正确。

### 5.5 为什么需要两层结构

AGENTIC-TEST-SPEC 应该分为：

```
上层（Harness-agnostic，跨环境复用）：
  - 测试意图："验证创建订单会扣减库存"
  - 业务条件：skuId, quantity, 预期库存变化
  - 依赖关系：需要先登录拿到 token

下层（Harness-specific，适配特定执行环境）：
  - 执行方式：Bash(curl -X POST ...)
  - 提取器：jq '.data.token'
  - 断言器：jq -e '.code == 0'
```

上层保持稳定（不随执行环境变化），下层适配不同的 Harness。

## 6. Spec 与 Harness

### 6.1 Harness 是什么

Harness = **Agent 的操作系统**。它定义了 Agent 的：

```
┌─────────────────────────────────────────────┐
│                 Harness 系统                 │
├─────────────────────────────────────────────┤
│  规则层：CLAUDE.md + settings.json          │
│         行为约束（必须跑 lint、多文件先出计划）│
├─────────────────────────────────────────────┤
│  能力层：Tools (Bash, Read, Write, Edit,    │
│         Glob, Grep, Agent, Workflow...)      │
├─────────────────────────────────────────────┤
│  控制层：Permission System + Sandbox         │
├─────────────────────────────────────────────┤
│  记忆层：Memory System + Conversation        │
├─────────────────────────────────────────────┤
│  调度层：CronCreate + ScheduleWakeup         │
├─────────────────────────────────────────────┤
│  编排层：TaskCreate + Workflow + Agent       │
└─────────────────────────────────────────────┘
```

### 6.2 Spec 和 Harness 的四维关系

```
维度 1: Spec → Harness（配置关系）
  Spec 的一部分定义 Harness 应该如何配置
  例：CLAUDE.md 中的验证链规则

维度 2: Harness → Spec（执行关系）
  Harness 读取 Spec，将其转化为可执行的行动
  例：AGENTIC-TEST-SPEC 的 YAML → Agent 通过 Bash 工具执行 curl

维度 3: Spec ← Harness（约束关系）
  Harness 的能力边界反向约束了 Spec 可以写什么
  例：如果 Harness 不支持浏览器自动化，Spec 就不能写 Playwright 测试

维度 4: Harness ← Spec（验证关系）
  Harness 用 Spec 来验证自己的输出是否正确
  例：Agent 修改代码后，验证链（Edit → Read → lint → test）由 Harness 强制执行
```

### 6.3 核心洞察：Spec 即 Harness 的递归结构

```
元元层：settings.json（定义 Harness 本身的行为边界）
  ↓ 约束
元层：CLAUDE.md（定义 Agent 的行为规范）
  ↓ 约束
语义层：PRD + 架构 + 规则（定义项目应该做什么）
  ↓ 约束
结构层：数据模型 + API 契约（定义项目怎么组织）
  ↓ 约束
验证层：AGENTIC-TEST-SPEC（定义如何验证）
  ↓ 执行
Harness 运行时：实际执行验证，反馈结果
  ↓ 反馈
回到元元层：根据反馈调整 settings.json
```

**每一层的 Spec 定义了下一层的约束，而最底层的 Harness 将最上层的 Spec 的意图兑现为可执行的验证。**

### 6.4 分工边界

| Harness 不该做（留给 Spec） | Spec 不该做（留给 Harness） |
|---------------------------|---------------------------|
| 业务规则（库存怎么恢复、折扣怎么算） | 如何执行测试（curl 还是 Supertest） |
| 数据格式（订单号几位） | 并发控制（一次开几个 Agent） |
| 状态迁移路径（pending → paid → confirmed） | 权限检查（哪些操作需要审批） |
| 错误码体系 | 重试策略（超时后重试几次） |

### 6.5 一个 Spec，多个 Harness

AGENTIC-TEST-SPEC 的真正价值在于——同一份 Spec 在多种 Harness 中执行：

| 执行环境 | 角色 | 触发时机 | 失败含义 |
|---------|------|---------|---------|
| Claude Code（开发中） | 即时反馈 | 每次代码修改后 | "你的改动破坏了某条规则，修复它" |
| CI Runner（PR） | 合入门禁 | PR 提交时 | "这个 PR 不能合并" |
| Pre-commit Hook | 本地拦截 | git commit 前 | "别提交，先修好" |
| Cron Job（线上） | 健康巡检 | 定时执行 | "线上出了问题，可能不是代码导致的" |

## 7. 演进路线：/init 之后

### 7.1 五阶段模型

```
阶段 1          阶段 2          阶段 3          阶段 4          阶段 5
/bootstrap/     /patch/         /structure/     /closed-loop/  /autonomous/

Harness: 盲的 → 看见坑了      → 知道规则了    → 主动守卫了    → 自举了
Spec:    空的 → 碎片化的      → 体系化的      → 可执行的      → 自我描述的
关系:    Harness 独存         → Spec 寄生     → Spec 独立     → Harness 消费 → 双向生成
```

### 7.2 各阶段详解

#### 阶段 1：Bootstrap（/init 刚执行完）

`/init` 扫描项目结构 → 推断技术栈 → 生成初始 CLAUDE.md（约 30 行，结构描述为主）。

**Harness**：只有结构感知，没有语义感知。知道 server/ 目录存在，但不知道里面涉及支付和库存。

**Spec**：一片空白。CLAUDE.md 是唯一的"文档"，本质上是 Harness 的自我描述。

**关系**：Harness ←→ 代码，没有任何 Spec 中介。

#### 阶段 2：Patch（踩坑积累）

**特征**：失败驱动学习。Agent 每次踩坑 → 人把教训写进 CLAUDE.md。

CLAUDE.md 开始长出两个区域：

- **已知注意事项**（异常知识，/init 不知道的）：Prisma 7 适配器、uni-app 构建不能用 npx
- **Agent 配置**（元 Spec）：多文件修改先出计划、Edit/Write 后 Read 确认

**Spec**：第一批独立文件出现，但大量信息散落在 CLAUDE.md 中，Spec 寄生在 Harness 文件里。

#### 阶段 3：Structure（campus-order 当前阶段）

**特征**：Spec 从 Harness 中剥离，形成独立体系。

- Spec 形成 DAG 依赖关系（7-10 份文档）
- Harness 退化为纯规则层（Agent 配置 + 验证链）
- CLAUDE.md 出现"Specs 参考文档"索引表

**当前局限**：Harness 知道 Spec 存在，但不消费 Spec 内容。Agent "应该"读 Spec，但 Harness 不强制执行。

#### 阶段 4：Closed-Loop（目标）

**特征**：Harness 从"被动引用"升级为"主动消费" Spec。

```
修改 server/src/order/order.service.ts
  ↓
Harness 查 Spec 索引：这个文件涉及哪些 Spec？
  → STATE-MACHINES §1（订单状态机）
  → BUSINESS-RULES §1-4（库存、折扣、退款、超时）
  ↓
Harness 自动：
  1. 加载相关 Spec 到 Agent 上下文
  2. 执行相关 AGENTIC-TEST 子集（增量，非全量）
  3. 检查修改是否违反 Spec 约束
```

**验证链进化**：从"全量验证"变为"增量验证"——根据修改文件定位相关测试子集。

**进入标志**：
1. AGENTIC-TEST-SPEC 成为 CI 关键路径
2. Spec 变更触发 Harness 行为变更
3. Harness 能检测 Spec 衰减（API-SPEC vs 代码路由不一致）
4. 验证从全量变为增量

#### 阶段 5：Autonomous（理论终点）

**特征**：Harness 参与 Spec 的生成和维护，关系发生反转。

- 代码变更 → Harness 自动同步 Spec（低风险变更）
- Harness 自动建议新规则 → 人确认 → 写入 CLAUDE.md
- 新增模块 → Harness 自动建议验证命令 → 写入验证链
- CLAUDE.md 本身也由 Harness 维护

### 7.3 不对称共演

Spec 和 Harness 的演进不是同步的，而是一个**交替领先的追赶过程**：

```
阶段 1: Harness 领先，Spec 追赶（从零开始）
阶段 2: Harness 继续领先（积累知识），Spec 追赶
阶段 3: 两者平齐，各司其职
阶段 4: Spec 领先（AGENTIC-TEST 新形态），Harness 追赶（能力升级）
阶段 5: Harness 追上并超越（自举），两者融合
```

阶段 3→4 的跃迁最困难——它需要 Harness 的能力升级，不是写文档能解决的。

## 8. Spec 发现方法：动手前如何识别

### 8.1 核心原理

**不遗漏 Spec 的关键：不是从"项目应该有什么文档"出发，而是从"工作流中的信息交接面"出发。**

任何一个软件开发过程，本质上是一条信息传递链。链上的每一个箭头都是一个**交接面**。交接面上需要 Spec 的条件是：

```
需要 Spec = (信息复杂度 > 阈值) OR (消费者无法直接追问生产者) OR (信息需要长期可追溯)
```

### 8.2 三步法

#### 步骤 1：画出工作流，标出所有交接面

把研发生命周期展开到"一个角色完成一件事"的粒度：

```
需求收集 → 需求评审 → 范围划定 → 架构设计 → 模块拆分 → 数据建模
  → 接口设计 → 状态机梳理 → 编码(后端) → 编码(前端) → 代码评审
  → 单元测试 → 集成测试 → E2E 测试 → 性能测试 → 部署 → 发布 → 运维
```

每个箭头标记：(a) 谁产出 (b) 谁消费 (c) 信息复杂度。

#### 步骤 2：对每个交接面判断是否需要 Spec

```
3 个以内的字段/规则 → 口头传递足够
3-10 个字段/规则 → 简要文档（一个表格）
10+ 个字段/规则 → 需要正式 Spec
涉及状态转换/条件分支 → 无论多简单都需要 Spec
```

#### 步骤 3：用三个交叉验证方法查漏

**方法 A：角色逆向遍历**

```
列出项目所有角色（含 Agent）
  ↓
对每个角色，列出它需要做的所有决策
  ↓
对每个决策，问：做出正确决策需要什么信息？
  ↓
反向检查：这些信息在哪份 Spec 中定义？
  ↓
如果没有 → 缺失，需要创建
```

**方法 B：异常路径压力测试**

对每个核心流程，追问每一步的异常：

```
"用户下单"流程：
  ✓ 正常：选择菜品 → 加购物车 → 提交 → 支付 → 取餐
  ✗ 购物车满了加不进 → 返回什么？前端怎么提示？
  ✗ 提交时库存被抢完 → 乐观锁冲突，重试几次？
  ✗ 支付成功但后端没收到回调 → 谁补偿查询？超时多久？
  ✗ 用户退款商家 24h 不处理 → 自动退款还是驳回？

每个 ✗ 都是一个潜在的 Spec 缺口。
```

**方法 C：交付物倒推**

```
最终交付什么？          需要什么 Spec 支撑？
源码包                  → 交付清单、模块白名单、版本号
Docker 镜像             → Dockerfile、环境变量、健康检查
数据库 Migration        → 数据模型、索引策略
API 文档（给客户）       → 完整 API-SPEC + 认证说明
管理后台（给客户）       → 部署手册、默认账号、首次配置指南
```

### 8.3 按风险排序

不是所有缺失的 Spec 都需要立刻补齐：

```
返工成本排序（从高到低）：
  1. 数据库/数据模型错误 → 迁移成本极高
  2. API 契约错误 → 前后端都要返工
  3. 状态机/业务规则错误 → 核心流程 Bug，影响支付/订单
  4. 架构决策错误 → 后期重构成本高
  5. 部署配置错误 → 线上故障
  6. PRD 遗漏 → 功能缺失，可后续迭代
  7. 测试用例遗漏 → Bug 逃逸，可补测
```

## 9. 实践建议

### 9.1 五项设计原则

#### 原则 1：读者中心设计（Audience-First）

每份 Spec 在开头声明目标读者和非目标读者。为特定读者的认知模型优化，不是"为所有人写同一份文档"。

#### 原则 2：最小充分信息（Minimal Sufficient Information）

充分性标准：把 Spec 和一个不了解项目的人关在房间里，他能否独立完成目标工作而不需要追问？

- 能 → 充分
- 不能 → 缺少关键信息

注意：最小充分信息 ≠ 最少信息。是在"信息量"和"维护成本"之间的最优解。

#### 原则 3：单一真相源（Single Source of Truth）

每一条事实只在一份 Spec 中"定义"，其他 Spec 只能"引用"。

```
事实类型 → 唯一定义源：
  功能需求        → PRD
  技术架构决策     → ARCHITECTURE
  表/字段/索引     → DATA-MODEL
  API 端点/参数    → API-SPEC
  状态迁移规则     → STATE-MACHINES
  计算/业务规则    → BUSINESS-RULES
  模块边界/依赖    → MODULES
  功能范围         → V1-SCOPE
```

注意：单一真相源指的是"定义权"的唯一性，不是"表述形式"的唯一性。同一事实可以被不同 Spec 用不同方式消费。

#### 原则 4：可验证性（Verifiability）

每一条陈述都应该是可验证的。"系统应该快速响应"不可验证；"P95 < 200ms"可验证。

注意：可验证性的要求按 Spec 层级分层——语义层可以宽松，验证层必须精确到机器可执行。

#### 原则 5：演进友好（Evolution-Friendly）

按变更频率分层组织信息，不要把"极稳"和"多变"的信息混在同一份 Spec 里：

- 低频（架构、核心规则）→ 手工精心维护
- 中频（端点清单、表结构）→ 半自动（代码生成 + 手工补充）
- 高频（测试用例、示例数据）→ 全自动（代码即真相）

### 9.2 常见反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| 散文版 Spec | "当用户点击下单按钮时，系统应先检查..." | 表格式、结构化："POST /api/orders，前置条件：购物车非空" |
| Spec 和代码矛盾 | 默认"以 Spec 为准" | 找出哪个更新，同步另一个；永远不默认 |
| 过早详细化 | 需求阶段就定义 API 的 exact JSON | 当前阶段能从第一性原理推导 → 可以写；否则 → 不写 |
| 用 Spec 替代沟通 | 写了 Spec 就不开会 | Spec 是沟通载体，不是沟通替代品 |
| 为所有人写同一份文档 | 一份 Spec 试图满足 PM + 开发 + QA | 每份 Spec 声明目标读者，为非目标读者提供 TL;DR |

### 9.3 规模适配

| 团队规模 | Spec 策略 |
|---------|---------|
| < 3 人 | 只保留 5 份核心 Spec：PRD（1 页纸）+ 数据模型 + API 契约 + 核心业务规则 + 测试关键路径 |
| 3-8 人 | 10-12 份 Spec：需求层 2 份 + 设计层 4 份 + 测试层 2 份 + 交付层 2 份 |
| 8-20 人 | 18-25 份 Spec：按矩阵全面覆盖，每份遵循"5 分钟可扫描"原则 |
| 50+ 人 | 33 份 + 跨团队协调 Spec |

### 9.4 对抗 Spec 腐烂

```
机制 1：Spec 生命周期标记
  - 活跃 → 衰减（3 月无更新）→ 废弃（6 月无更新）→ 归档

机制 2：CI 兜底检查
  - API 路由 vs Spec 端点数 → 不一致时 CI 告警
  - Prisma schema vs DATA-MODEL 表数 → 不一致时 CI 告警

机制 3：自动化率提升
  - 离代码越近的 Spec，自动化程度越高，寿命越长
  - API-SPEC（80% 可自动化）寿命远长于 PRD（0% 可自动化）
```

## 10. 行业对标

### 10.1 各行业 Spec 实践

| 行业/标准 | 核心思想 | 可借鉴之处 |
|----------|---------|-----------|
| **NASA DO-178C** | 生命周期数据（LCD）严格按阶段产出，每份数据有"派生自"追溯链 | 需求→测试的双向追溯矩阵 |
| **ISO 26262**（汽车） | 安全需求→架构设计→单元设计→单元测试，层次严格 | 分层思想，下级追溯上级 |
| **IEC 62304**（医疗） | 变更必须同步更新所有受影响文档 | 变更影响分析机制 |
| **Google Design Doc** | 轻量级：目标、非目标、设计、替代方案、交叉关注点 | ADR（架构决策记录）格式 |
| **Stripe API** | 以 API 为中心，代码即 Spec（文档从注解自动生成） | API-SPEC 自动生成 |
| **RFC 流程** | 提案→草案→标准→废弃，每个状态有进入/退出条件 | Spec 版本管理和废弃机制 |

### 10.2 真正的对标对象：Spec + Runtime 组合

纯 Spec 对标不够。真正应该对标的是那些"Spec 有配套 Runtime"的成熟系统：

| 系统 | Spec 层 | Runtime 层 | 启示 |
|------|---------|-----------|------|
| **AWS CloudFormation** | YAML/JSON 模板 | CloudFormation Engine | Spec 定义目标状态，Runtime 负责达成 |
| **Terraform** | HCL 配置 | Terraform CLI | Spec 和 Runtime 独立演进 |
| **Kubernetes** | YAML 清单 | Controller Manager | Spec 声明期望，Controller 持续 reconcile |
| **GitHub Actions** | YAML workflow | Actions Runner | Spec 定义 CI 流程，Runner 执行 |
| **本项目** | CLAUDE.md + AGENTIC-TEST-SPEC | Claude Code Harness | Spec 定义约束，Harness 执行验证 |

### 10.3 与 campus-order 的差距

| 差距 | 严重程度 | 改进方向 |
|------|:--------:|---------|
| 缺少需求→测试双向追溯矩阵 | 中 | QA-TEST-SPEC 加一列"覆盖 PRD 条目" |
| Spec 没有版本号和变更日志 | 中 | 每个文件加 frontmatter |
| API-SPEC 与代码不同步 | 高 | Swagger 自动生成 + 手工补充语义 |
| 缺少 Spec 变更影响分析 | 中 | SPEC.md 加影响矩阵 |
| 缺少部署/运维 Spec | 低 | 新建 DEPLOYMENT.md |
